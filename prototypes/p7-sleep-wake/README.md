# Прототип P-7: усыпление и пробуждение фич

**Этап 0, одноразовый код.** Проверяет из [плана этапа 0](../../docs/stage-0-plan.md) и [user-flows.md](../../docs/product/user-flows.md#4-жизненный-цикл-окружения):

- неактивная фича засыпает, активная (запросы или правки файлов) — нет;
- первый запрос будит фичу: браузер видит страницу «Запускаем», API-клиент просто ждёт ответа;
- пробуждение укладывается в NFR-3 (< 10 с), запросы во время перехода не теряются;
- бюджет ресурсов усыпляет самую давно неактивную фичу, main не засыпает никогда.

**Критерий успеха — пробуждение < 10 с — выполнен.** Все 16 проверок прошли.

## Как устроено

```
                      ┌──────────── агрегатный кластер agg-pay-1 ────────────┐
Host: pay-1… ─▶ Envoy │ 1) pay-1-payments  (здоров → весь трафик сюда)        │
                      │ 2) waker           (только пока pay-1 нездоров)       │
                      └───────────────────────────────────────────────────────┘
                                  health check pay-1-payments ─▶ waker /_waker/health/pay-1
```

- **Маршруты не меняются никогда.** Маршрут фичи ведёт в агрегатный кластер Envoy: сначала модуль фичи, при отказе — будильник. Конфиг Envoy статический.
- **Здоровье фичи объявляет агент, а не TCP-проба.** Health check модуля в Envoy спрашивает будильник (`health_check_config.address`). В агенте с xDS это будет `health_status` в EDS.
- **Усыпление.** Будильник объявляет фичу нездоровой, ждёт, пока Envoy начнёт слать её трафик ему, и только потом делает `docker stop`.
- **Пробуждение.** Запрос, пришедший к будильнику, запускает `docker start` один раз на все параллельные запросы. Будильник ждёт, пока модуль начнёт принимать TCP, и отправляет удержанный запрос (с телом) **прямо в модуль** — по адресу из заголовка `x-docklet-upstream`, который ставит маршрут. Браузеру (`Accept: text/html`), если старт дольше 300 мс, отдаётся страница «Запускаем…» с автообновлением.
- **Активность.** Счётчики `upstream_rq_total` кластеров фичи в Envoy плюс самое свежее время изменения файлов в worktree (без `.git`, `node_modules`, `vendor`).
- **Бюджет.** `MAX_RUNNING`: после пробуждения засыпают самые давно неактивные фичи. Main будильник не трогает.

| Сервис | Что это |
|---|---|
| `envoy` | Вход `127.0.0.1:18095`, конфиг [envoy/envoy.yaml](envoy/envoy.yaml) |
| `waker` | Часть агента: усыпление, пробуждение, активность, бюджет ([waker/main.go](waker/main.go)) |
| `backend` | main, не управляется будильником |
| `pay-1` | Python + свой Postgres; запрос пишет в БД |
| `ui-2` | Node |
| `slow-3` | Node, который 3 с «загружается» перед тем, как слушать порт (как Spring или Rails) |

```bash
go run .          # поднимает стенд, прогоняет сценарии, печатает отчёт, удаляет стенд
go run . -keep    # оставить стенд
```

## Как к этому пришли: что не сработало

Первая версия угадывала здоровье фичи TCP-пробой в контейнер, находила контейнер по DNS-имени и возвращала удержанный запрос обратно через Envoy. Результаты:

| Сценарий | Первая версия | Причина |
|---|---|---|
| 20 одновременных запросов к спящей фиче | 13/20 и 16/20 ответов 200 | Повтор через Envoy снова попадал к будильнику: рабочие потоки Envoy переключаются обратно не одновременно. Ещё часть запросов уходила на старый IP контейнера, который сменился после `docker start` |
| Запрос сразу после усыпления | 1 из 5 — 503 | Envoy ещё считал остановленный контейнер здоровым |
| Пробуждение | 1,3–2,0 с | Удержанный запрос ждал, пока Envoy заново увидит фичу здоровой |

Четыре изменения убрали все ошибки и ускорили пробуждение в 5–10 раз:
1. Здоровье объявляет агент.
2. Перед остановкой агент переключает трафик на будильник.
3. IP контейнеров фич закреплены, а кластеры Envoy статические.
4. Удержанные запросы идут прямо в модуль.

## Выводы

1. **Пробуждение стоит столько же, сколько запуск самого приложения**, плюс около 0,1–0,15 с на `docker start`. Платформа укладывается в NFR-3 с огромным запасом. Если фича просыпается дольше 10 с, причина — время загрузки приложения, и панель должна так и говорить.
2. **Конфиг Envoy при усыплении и пробуждении не меняется.** Агрегатный кластер «модуль → будильник» плюс здоровье, которое объявляет агент, полностью закрывают переключение. Это хорошо ложится на xDS: агенту достаточно менять `health_status` эндпоинта в EDS.
3. **Здоровье фичи — это решение агента, а не догадка прокси.** TCP-проба и DNS дают окна, в которых запросы теряются. Правильный порядок усыпления: «объявить нездоровой → дождаться, пока трафик уйдёт → остановить».
4. **Агент должен закреплять IP контейнеров фич.** Подсеть на окружение он и так выделяет ([P-1/P-2](../p1-p2/README.md)). После `docker start` IP может смениться, и прокси уйдёт на старый адрес.
5. **У Envoy есть ловушка в настройках по умолчанию:** без трафика кластер проверяется раз в 60 с (`no_traffic_interval`). У спящей фичи трафика нет по определению, так что параметр надо уменьшать.
6. **Контейнерам фич нужен init (`init: true`).** Процесс с PID 1 без обработчика SIGTERM (Python, Node) игнорирует `docker stop`, и каждое усыпление ждёт SIGKILL по таймауту.
7. **Активность по запросам и по файлам работает как задумано.** Правка файла без единого запроса держит фичу живой — это важно для разработчика, который пишет код и ещё не открыл страницу. В агенте вместо обхода worktree раз в секунду нужны FSEvents/inotify.
8. **Удержанный POST безопасен,** потому что повтор идёт один раз и прямо в модуль. Параллельные запросы будят фичу один раз.

## Что не проверено

- Падение модуля в работающей фиче: по задумке здоровье следует за фактическим состоянием, и следующий запрос перезапустит фичу. Отдельно не проверялось.
- Удержание дольше 60 с, WebSocket и gRPC к спящей фиче.
- Воркеры и cron в спящей фиче: сообщения в её очереди копятся, пока она спит.
- Фича из нескольких модулей с разными адресами: в стенде у каждой фичи один модуль.
- FSEvents/inotify вместо обхода файлов; xDS вместо статического конфига.
