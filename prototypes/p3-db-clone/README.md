# Прототип P-3: клонирование Postgres

**Этап 0, одноразовый код.** Отвечает на вопросы из [плана этапа 0](../../docs/stage-0-plan.md) и [ADR-0007](../../adr/0007-db-cloning.md):

1. Укладывается ли клон БД фичи в требование NFR-2 (< 60 с при БД до 1 ГБ) на Docker Desktop, где тома лежат на ext4 без reflink?
2. Какую стратегию `CREATE DATABASE … TEMPLATE` использовать?
3. На сколько обновление золотой копии блокирует main?
4. Насколько вариант «отдельный инстанс на фичу» (копия каталога данных) дороже клона внутри инстанса?

## Как устроен стенд

`main.go` для каждого варианта окружения:

1. Поднимает Postgres и наполняет базу `app` через `pgbench -i` (масштаб 68 ≈ 1 ГБ).
2. Создаёт **золотую копию** так, как её будет создавать агент: `ALTER DATABASE app ALLOW_CONNECTIONS false` → `pg_terminate_backend` → `CREATE DATABASE golden TEMPLATE app` → `ALLOW_CONNECTIONS true`. Параллельно цикл подключений к `app` измеряет самый длинный промежуток, когда main недоступна.
3. Клонирует `golden` в базы фич каждым способом, время — по `\timing` на сервере, медиана из N прогонов. Считает, сколько места на диске добавил клон, и сверяет число строк в клоне.
4. Копирует весь `PGDATA` после `CHECKPOINT` (`cp -a`, на XFS — `--reflink=always`). Это оценка варианта «отдельный инстанс на фичу», только по времени.

Варианты окружения:

| Ключ | Что | Зачем |
|---|---|---|
| `pg17-ext4` | PostgreSQL 17, том Docker | Текущая версия у большинства проектов |
| `pg18-ext4` | PostgreSQL 18, том Docker | Как будет у пользователя Docker Desktop по умолчанию: ext4 без reflink |
| `pg18-xfs` | PostgreSQL 18, данные на XFS с `reflink=1` (loop-устройство внутри VM) | Как будет на ФС с copy-on-write: XFS/btrfs на Linux, APFS, возможно OrbStack |

```bash
go run . -size 1 -runs 3                       # все варианты, 1 ГБ
go run . -size 5 -runs 1 -targets pg18-ext4    # один вариант, 5 ГБ
```

## Выводы

1. **NFR-2 по БД выполняется с запасом даже без reflink.** Клон 1 ГБ на ext4 в Docker Desktop занимает 0,4–0,6 с, 5 ГБ — 2,5–3 с. Опасение из `data.md` («на ext4 копия за секунды не гарантирована») по **времени** не подтвердилось: быстрый NVMe и кэш страниц VM справляются. Оговорка: 1 ГБ целиком помещается в кэш VM (8 ГБ); холодный кэш не мерили.
2. **Настоящая цена ext4 — место на диске, а не время.** Каждый клон без reflink — полная копия: 10 фич на базе 5 ГБ — это 50 ГБ. С reflink клон занимает 0 байт до первых изменений. Бюджет ресурсов устройства должен учитывать диск, а не только RAM.
3. **Стратегию задаём явно: всегда `FILE_COPY`.** `WAL_LOG` (по умолчанию с PG 15) в 3–4 раза медленнее и дополнительно пишет WAL.
4. **На PG 18 всегда ставим `file_copy_method = clone`.** На ФС с reflink клон становится мгновенным (33–49 мс независимо от размера). На ext4 это не ошибка: Postgres использует `copy_file_range`, время такое же, как у `copy`. Определять ФС заранее не нужно.
5. **Обновление золотой копии ненадолго отключает main:** около 0,6 с на 1 ГБ на ext4 (3,8 с на 5 ГБ), около 0,2 с с reflink независимо от размера. В это время новые подключения к main получают ошибку, а не ждут. Делать это только после миграций main и показывать в панели. Для больших баз без reflink нужен способ мягче — например, пауза подключений в пулере. Это открытый вопрос.
6. **Клон внутри инстанса дешевле отдельного инстанса.** Копия всего `PGDATA` тянет за собой WAL и служебные базы: 3 с вместо 0,5 с на 1 ГБ, плюс RAM на ещё один Postgres. Отдельный инстанс оставляем только для проектов с жёстко заданным именем БД, как и записано в `data.md`.
7. **Нехватка места ломает Postgres неочевидно.** Когда XFS переполнился, следующий клон упал не с «нет места», а с `buffer is pinned in InvalidateBuffer`. Агент должен проверять свободное место до клонирования: без reflink нужно не меньше размера золотой копии плюс запас.
8. **Reflink в Docker Desktop достижим, но с ценой.** XFS на loop-устройстве внутри VM даёт мгновенные клоны, но обычная запись медленнее: наполнение 5 ГБ заняло 28 с против 17 с на томе. Для MVP оставляем обычные тома. Отдельный XFS-том под базы — опция на потом, если пользователям станет не хватать диска.

## Что не проверено

- **APFS** нативно и **OrbStack** (ожидается reflink на его ФС): нужен прогон на машине с OrbStack.
- **Linux-хост с XFS/btrfs** без loop-устройства.
- Холодный кэш и базы больше RAM VM (10+ ГБ).
- MySQL — прототип **P-4**.
- Встраивание клона в CLI прототипа P-1/P-2: сейчас фича там получает пустой инстанс с миграциями.

## Проверка на Colima и OrbStack (14.10.2026)

Тот же стенд, вариант «том Docker», PostgreSQL 18, база 1 ГБ, медиана из 3:

| Runtime | ФС томов | `FILE_COPY` + `copy` | `FILE_COPY` + `clone` | Место за клон (`clone`) | Золотая копия (main недоступна) |
|---|---|---|---|---|---|
| Docker Desktop | ext4 | 0,46 с | 0,42 с | 1025 МБ | 0,57 с |
| Colima (vz) | ext4 | 0,72 с | 0,55 с | 1025 МБ | 0,99 с |
| **OrbStack** | **btrfs** | 0,72 с | **176 мс** | **0 МБ** | 1,28 с |

**OrbStack хранит тома на btrfs, и `file_copy_method = clone` даёт настоящий copy-on-write на обычном томе**, без loop-устройства. Для команд с большими базами OrbStack — лучший runtime на Mac: клон почти мгновенный и не занимает места до первых изменений. Colima, как и Docker Desktop, — ext4 без reflink.
