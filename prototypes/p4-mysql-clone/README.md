# Прототип P-4: клонирование MySQL

**Этап 0, одноразовый код.** Закрывает открытый вопрос из [ADR-0007](../../adr/0007-db-cloning.md) и `risks-and-open-questions.md`: у MySQL нет `CREATE DATABASE … TEMPLATE`, как получить копию базы для фичи так же быстро, как в Postgres?

## Что сравнивали

| Способ | Как работает | Где живёт копия |
|---|---|---|
| `mysqldump → mysql` | Логический дамп золотой схемы и загрузка в новую схему | Новая схема в инстансе main |
| Transportable tablespaces | `CREATE … LIKE` + `DISCARD TABLESPACE`, затем `FLUSH TABLES … FOR EXPORT`, копирование `.ibd`/`.cfg` (на XFS — `cp --reflink`), `IMPORT TABLESPACE` | Новая схема в инстансе main |
| **Отдельный инстанс** | Золотой инстанс делается через `CLONE LOCAL DATA DIRECTORY` (встроенный clone plugin), затем копия его каталога (на XFS — `cp --reflink`) и запуск отдельного `mysqld` | Отдельный `mysqld` на фичу |

Золотую копию стенд делает двумя способами и меряет, насколько при этом блокируется запись в main. Параллельно идёт цикл `INSERT` в базу main.

База: одна таблица на 4,1 млн строк + 200 маленьких таблиц, всего 1114 МБ. Число таблиц важно: часть способов платит за каждую таблицу.

```bash
docker build -t devcorb-proto/p4-mysql:8.4.3 .
go run . -size 1 -runs 3          # ext4 и XFS с reflink
go run . -size 1 -targets ext4
```

## Результаты

14.10.2026 · macOS 26, Apple Silicon · Docker Desktop 29.8, VM: 8 ГБ RAM · MySQL 8.4.3. Во всех вариантах число строк в клоне совпало с оригиналом.

### Клон базы фичи, 1,1 ГБ, 202 таблицы (медиана из 3)

| Способ | ext4 | XFS reflink | Место за клон: ext4 / XFS |
|---|---|---|---|
| `mysqldump → mysql` | 25,8 с | 37,5 с | 1970 / 2139 МБ |
| Transportable tablespaces | 5,8 с (`IMPORT` 202 таблиц — 3,3 с) | 11,3 с (`IMPORT` — 8,4 с) | 1114 / **1114** МБ |
| **Отдельный инстанс из золотого** | **1,9 с** | **1,2 с** | 1367 / **131** МБ |

Время отдельного инстанса включает копирование каталога и запуск `mysqld` до ответа на `ping`.

### Золотая копия: цена для main

| Способ | ext4 | XFS reflink | Запись в main заблокирована |
|---|---|---|---|
| **`CLONE LOCAL`** (золотой инстанс) | 0,53 с | 1,2 с | **≤ 20–40 мс** (обычный интервал проб — 10–14 мс) |
| Transportable tablespaces (золотая схема) | 13,6 с | 11,9 с | 0,3–0,9 с |

### Память инстанса фичи (RSS сразу после старта)

| Настройки `mysqld` | RSS |
|---|---|
| По умолчанию, buffer pool 128 МБ | 423 МБ |
| + `performance_schema=OFF` | 188 МБ |
| + buffer pool 32 МБ, `max_connections=20`, малые кэши таблиц | **120 МБ** |
| Для сравнения: main с buffer pool 1 ГБ | 558 МБ |

## Выводы

1. **Для MySQL — отдельный инстанс на фичу из золотого инстанса.** Он быстрее всех: 1,9 с на ext4 и 1,2 с с reflink. Скорость не зависит от числа таблиц. Только при нём reflink реально экономит диск: 131 МБ на клон вместо 1,1 ГБ. Дополнительный плюс: имя базы в фиче не меняется, `DATABASE_URL` проекта не трогаем, меняется только хост.
2. **Золотой инстанс обновляем через `CLONE LOCAL`.** Это почти не мешает main: запись блокируется не дольше 20–40 мс, подключения не рвутся. В этом месте MySQL удобнее Postgres, где золотая копия отключает main на 0,6 с на гигабайт ([P-3](../p3-db-clone/README.md)).
3. **Transportable tablespaces не подходят.** На каждую таблицу уходит около 16 мс на `IMPORT`, то есть 3–16 с на реальных схемах из 200–1000 таблиц. Создание золотой схемы блокирует запись в main почти на секунду. Главное: `IMPORT TABLESPACE` переписывает каждую страницу, поэтому reflink не экономит ни байта. На loop-устройстве это ещё и медленнее.
4. **`mysqldump` годится только как запасной путь для маленьких баз:** 26 с на 1 ГБ и почти двойной расход места из-за пересоздания индексов и redo.
5. **Цена отдельного инстанса — память, и её надо урезать.** С настройками по умолчанию инстанс фичи занимает 423 МБ, и половина из них — `performance_schema`. Агент запускает инстансы фич с бережливыми настройками (`performance_schema=OFF`, маленький buffer pool) — около 120 МБ сразу после старта. Под нагрузкой buffer pool заполнится до заданного размера. Бюджет ресурсов должен считать каждую фичу с MySQL как отдельный процесс.
6. **Сравнение с Postgres:** там лучший вариант — новая база внутри инстанса через `TEMPLATE`, в MySQL — отдельный инстанс. Модель данных агента должна поддерживать обе схемы: «клон = база в общем инстансе» и «клон = свой контейнер БД». Вторая уже реализована в прототипе P-1/P-2.

## Что не проверено

- MariaDB: clone plugin там нет, нужен другой путь (`mariabackup`).
- APFS/OrbStack и Linux-хост с XFS/btrfs без loop-устройства.
- Базы больше 1 ГБ и холодный кэш.
- `mydumper`/`myloader`: параллельный логический дамп. Вряд ли обгонит отдельный инстанс, но это вариант для MySQL 5.7, где нет clone plugin.
- Поведение `CLONE LOCAL` при активной нагрузке на запись (здесь — один `INSERT` за раз).
