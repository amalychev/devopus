# Прототип P-5: Contextual Isolation через W3C Baggage

**Этап 0, одноразовый код.** Проверяет главную гипотезу отличия продукта из [плана этапа 0](../../docs/stage-0-plan.md) и [routing.md](../../docs/architecture/routing.md): фича форкает только изменённый модуль, а неизменённые модули main, вызванные из фичи, сами попадают в форк. Маршрут выбирает Envoy по заголовку `baggage`, а OpenTelemetry пробрасывает этот заголовок через модули без правок их кода.

**Критерий успеха:** базовый бэкенд, вызванный из фичи, попадает в форкнутую платёжку; очередь с префиксом работает. **Выполнен.**

## Стенд

```
браузер ─ Host: pay-123.shop.localhost ─▶ Envoy edge :8080
                                           │ удаляет baggage клиента, ставит feature=pay-123
                                           ▼
                   backend-node / backend-python / backend-php   (только main, без форков)
                                           │ GET http://payments/…  + baggage (OpenTelemetry)
                                           ▼
                                      Envoy mesh :80   ← «payments» — сетевой алиас Envoy
                       feature=pay-123 ─▶ payments-pay-123
                       feature=pay-124 ─▶ payments-pay-124
                       иначе           ─▶ payments-main
```

| Сервис | Что это |
|---|---|
| `envoy` | Вход `:8080` (на хосте `127.0.0.1:18090`) и внутренняя маршрутизация `:80`. Логическое имя `payments` — сетевой алиас Envoy, а не какой-либо копии ([envoy/envoy.yaml](envoy/envoy.yaml)) |
| `backend-node` | Node 22, голый `http`, вызовы через `http.get` и `fetch`, `@opentelemetry/auto-instrumentations-node` 0.50 |
| `backend-python` | Flask + `requests`, `opentelemetry-instrument` 0.48b0; плюс эндпоинт с голым `http.client` и постановка задач в очередь |
| `backend-php` | PHP 8.3, Slim + Guzzle, `ext-opentelemetry` 1.1 + `opentelemetry-auto-slim` / `-auto-guzzle` |
| `payments-main`, `payments-pay-123`, `payments-pay-124` | Заглушка платёжки: отвечает, какой экземпляр обработал вызов и какой `baggage` получил |
| `worker-main`, `worker-pay-123` | Воркеры очереди Redis; `pay-123` форкает и воркер, `pay-124` — нет |

Фича `pay-123` = форк `payments` + `worker`. Фича `pay-124` = форк только `payments`. Бэкенды во всех фичах общие из main.

```bash
go run .          # поднимает стенд, прогоняет проверки, печатает отчёт, удаляет стенд
go run . -keep    # оставить стенд для ручных проверок
```

## Выводы

1. **Главная гипотеза подтверждена.** Неизменённый бэкенд main на Node, Python и PHP, вызванный из фичи, попадает в форк. Сделано без единой строки кода про фичи в бэкендах: только автоинструментация OpenTelemetry и `OTEL_PROPAGATORS=tracecontext,baggage`. Фича стоит один контейнер вместо пяти.
2. **Envoy почти бесплатен:** +0,1 мс на внутренний вызов при цели 2 мс. Разбор baggage регулярным выражением на этом фоне не заметен.
3. **Node: `OTEL_TRACES_EXPORTER=none` молча выключает передачу контекста** (`auto-instrumentations-node` 0.50). В Python и PHP та же настройка контекст не трогает. Агент не должен отключать экспорт трейсов. Если проекту трейсы не нужны, ставим `OTEL_TRACES_SAMPLER=always_off`: спаны не пишутся, контекст передаётся. Если в проекте уже настроен свой OpenTelemetry, агент добавляет только пропагатор `baggage` и ничего не переопределяет.
4. **Неинструментированный клиент теряет контекст без ошибок.** Голый `http.client` в Python молча уходит в main. Пользователь увидит «фича не работает», а не ошибку. Проверка распространения из `routing.md` (7.4) обязательна. В прототипе она сделана через ответы модулей; в агенте — через пробный запрос и трейсы.
5. **Очереди не работают «из коробки» — нужны две правки в коде проекта.** Отправитель должен класть контекст в сообщение и выбирать очередь (`queue_for(feature)` по таблице форков от платформы). Воркер должен восстанавливать контекст из сообщения (`context.attach(propagate.extract(...))`). Для Celery, BullMQ и Sidekiq есть готовая инструментация, для голых списков Redis — нет. Платформе нужен маленький SDK для очередей и таблица форков, доступная модулям (в прототипе — `forks.json`).
6. **Схема «воркер main обрабатывает сообщения фичи» работает:** без форка воркера сообщение `pay-124` взял воркер main, но его вызов ушёл в форк `pay-124`. Обратное тоже проверено: воркер main не берёт сообщения из `jobs:pay-123`. Но воркер main с данными фичи пишет в общую БД — это то же ограничение «общий модуль пишет в общие данные» из `data.md`.
7. **Удалять на входе нужно только ключ `feature`, а не весь заголовок.** Прототип удаляет `baggage` целиком: это безопасно, но ломает проекты, которые сами пользуются baggage. В агенте нужен фильтр, который удаляет только ключ `feature` (Lua или ext_proc в Envoy).
8. **PHP требует инструментации фреймворка.** Контекст из входящего запроса берёт `opentelemetry-auto-slim`; на голом PHP-скрипте без Slim, Laravel или PSR-15 извлекать его будет некому. Сюда же относится Python: голый `http.server` не инструментирован, поэтому в стенде Flask. Это нужно проверять в панели и предлагать Simple Isolation.
9. **Зависимости OTel хрупкие.** `opentelemetry-instrument` 0.48b0 падает без `setuptools` в slim-образе Python. Агент должен поставлять готовые образы рантаймов с проверенными версиями, как и записано в `routing.md` про `ext-opentelemetry`.

## Что не проверено

- Проверка распространения через трейсы OpenTelemetry (коллектор + анализ) — здесь только по ответам модулей.
- Laravel, Django, Express, NestJS и другие фреймворки; gRPC и WebSocket — по документу они остаются в Simple Isolation.
- Celery, BullMQ, Sidekiq с их родной инструментацией.
- Генерация конфига Envoy из списка фич и xDS — здесь конфиг написан руками на две фичи.
- Удаление только ключа `feature` из baggage на входе.
