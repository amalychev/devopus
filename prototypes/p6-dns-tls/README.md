# Прототип P-6: порты, `*.localhost` и локальный CA

**Этап 0, одноразовый код.** Проверяет решения из [local-networking.md](../../docs/architecture/local-networking.md) и [ADR-0011](../../adr/0011-privileged-helper.md) на реальных клиентах: curl, Python, Node, PHP, Java и Go.

- Кто резолвит `*.localhost` без настройки, на хосте и в контейнерах?
- Как занять порты 80/443 на loopback без root и без `0.0.0.0`?
- Реален ли риск с IPv6?
- Доверяют ли клиенты локальному CA и защищают ли Name Constraints от кражи его ключа?
- Как отдать CA контейнерам, не пересобирая образы?

**Стенд не меняет системных настроек и не требует root.** `/etc/resolver`, launchd-демон и установка CA в связку ключей macOS не проверялись: на рабочей машине это изменения, требующие согласия пользователя. Как показали результаты, для macOS 26 с Docker Desktop они и не нужны.

```bash
go run .              # все разделы: host, containers, linux
go run . containers   # один раздел
```

## Результаты

### Внутри контейнеров

Сеть окружения, Envoy (TLS по SNI) и CoreDNS: `*.localhost` → Envoy, остальное — во встроенный DNS Docker.

| Проверка | Результат |
|---|---|
| `app.shop.localhost` без CoreDNS (getaddrinfo) | не резолвится |
| С CoreDNS: `app.shop.localhost`, `pay-123.app.shop.localhost` | ✅ → адрес Envoy |
| С CoreDNS: имена контейнеров | ✅ резолвятся, как раньше |
| **curl с CoreDNS** | ⚠️ **DNS не спрашивает**: по RFC 6761 сразу идёт на `[::1]` и `127.0.0.1`. Headless Chromium по документации ведёт себя так же |
| Python, Node, PHP: `https://app.shop.localhost` без настройки | отказ: CA неизвестен |
| Python, Node, PHP: с CA от агента (env) | ✅ работают |
| curl с CA от агента | ⚠️ всё равно не работает: уходит на loopback |
| curl + relay `127.0.0.1:443 → Envoy` в сетевом пространстве модуля | ✅ работает |
| Все четыре клиента, любой режим: `evil.example.com` | ✅ отклонён (Name Constraints) |
| Все четыре клиента с CA от агента: публичный `https://example.com` | ✅ работает — подмена хранилища ничего не ломает |

Как агент отдаёт CA контейнеру, не меняя образ: монтирует `/devopus/ca.pem` и `/devopus/bundle.pem` (публичные корни + наш CA) и задаёт:

| Переменная | Кто читает |
|---|---|
| `SSL_CERT_FILE=/devopus/bundle.pem` | OpenSSL: curl, Python `ssl`/urllib, PHP |
| `NODE_EXTRA_CA_CERTS=/devopus/ca.pem` | Node: добавляет к своим корням |
| `REQUESTS_CA_BUNDLE=/devopus/bundle.pem` | Python `requests` (certifi) |
| `CURL_CA_BUNDLE=/devopus/bundle.pem` | curl |

## Выводы

1. **На macOS 26 не нужен ни `/etc/resolver`, ни локальный DNS.** Все шесть клиентов резолвят `*.localhost` системным резолвером. Root на этом шаге не нужен, установка упрощается. На старых macOS это надо перепроверить, прежде чем удалять шаг из установщика.
2. **На Mac с Docker Desktop не нужен свой launchd-помощник для портов.** Без root открыть `127.0.0.1:80` нельзя, а `0.0.0.0` открывать нельзя нам. Но Docker Desktop публикует привилегированные порты на `127.0.0.1` и `::1` своим помощником. Значит, Envoy на Mac запускается **контейнером** с `-p 127.0.0.1:80:…` и `-p [::1]:80:…`. Свой launchd-помощник нужен, только если Envoy работает на хосте: OrbStack и Colima ещё не проверены.
3. **Риск с IPv6 реален и бьёт по всем клиентам.** Резолвер отдаёт `::1` первым, и curl, Python, Node идут к тому, кто слушает `::1`. Envoy обязан слушать `127.0.0.1` **и** `::1`, а `doctor` должен проверять занятость обоих адресов. Это уже записано в `local-networking.md` и подтверждено.
4. **Java 25 игнорирует Name Constraints у корневого сертификата.** С одним корневым CA украденный ключ позволяет подделать любой сайт для Java-клиентов, которым мы этот CA дали. **Решение проверено:** корень с ограничениями подписывает промежуточный CA с теми же ограничениями, ключ корня сразу уничтожается, агент хранит только ключ промежуточного. Ограничения промежуточного Java проверяет, и все шесть клиентов отвергают чужой домен.
5. **CoreDNS в сети окружения решает `*.localhost` в контейнерах для обычных HTTP-библиотек**, не ломая имена контейнеров и любой уровень вложенности.
6. **curl и headless Chromium внутри контейнеров DNS не спрашивают**, а `*.localhost` у них всегда loopback. Сценарий «PDF по URL через headless Chrome» из `local-networking.md` с одним CoreDNS не заработает. Проверенный обход — relay на `127.0.0.1:443` в сетевом пространстве модуля (sidecar). На порт 80 он не подходит: модуль сам слушает 80. Другие варианты: публиковать для SSR внутренний URL окружения или `--host-resolver-rules` для Chromium. Решение — в объёме этапа 1, отдельным пунктом.
7. **CA в контейнеры отдаём переменными окружения, без пересборки образов.** Публичные сайты при этом продолжают работать, потому что `bundle.pem` содержит и публичные корни. Java в контейнерах так не настроить — нужен отдельный truststore (`-Djavax.net.ssl.trustStore`, проверено на хосте).
8. **Linux: `setcap cap_net_bind_service` на бинарник прокси работает** при обычном `ip_unprivileged_port_start`. `nss-myhostname`, который есть на хостах с systemd, резолвит `*.localhost` в loopback.

## Что не проверено

- Установка CA в связку ключей macOS и в NSS Firefox (нужно согласие пользователя).
- launchd socket activation: по выводу 2 он не нужен для Docker Desktop, но может понадобиться для OrbStack и Colima.
- `/etc/resolver` и локальный DNS на старых macOS; VPN, переписывающий DNS.
- Windows целиком (NRPT, WSL2): этап 3.
- Headless Chromium в контейнере: поведение взято из документации, не измерено.
- Java внутри контейнеров.

## Проверка на Colima и OrbStack (14.10.2026)

| Проверка | Docker Desktop | Colima | OrbStack |
|---|---|---|---|
| Публикация `127.0.0.1:81` и `[::1]:81` без root | ✅ | ✅ | ✅ |
| Кто слушает на хосте | `127.0.0.1:81` | ⚠️ `*:81` (`limactl`) | ⚠️ `*:81` (OrbStack) |
| TCP на LAN-адрес машины | закрыт | принимает и сразу закрывает | принимает и сразу закрывает |
| HTTP с LAN-адреса до контейнера | нет | нет | нет |
| CoreDNS для `*.localhost` в контейнерах | ✅ | ✅ | ✅ |
| CA через переменные окружения (Python, Node, PHP) | ✅ | ✅ | ✅ |
| curl + relay `127.0.0.1:443` | ✅ | ✅ | ✅ |

**Colima и OrbStack на просьбу опубликовать порт на `127.0.0.1` слушают `*:порт`**, то есть все интерфейсы: без root на macOS иначе не открыть привилегированный порт. Трафик с внешнего адреса они не пересылают — соединение принимается и сразу закрывается. Данные не утекают, но порт на LAN-интерфейсе открыт: это отступление от правила «никогда не `0.0.0.0`», и брандмауэр macOS может спросить разрешение. Проверено только с самой машины, не с другого хоста. Docker Desktop слушает строго `127.0.0.1`.

Мелкие отличия: на Colima без CoreDNS `*.localhost` в контейнере резолвится в `127.0.0.1` (итог тот же — loopback контейнера). На OrbStack запросы к внешним именам до `--dns` не доходят, их обслуживает сам OrbStack; для `*.localhost` CoreDNS работает.
