# Прототип P-1 + P-2

**Этап 0, одноразовый код.** Проверяет две гипотезы из [плана этапа 0](../../docs/stage-0-plan.md):

- **P-1:** по `workspace.yaml` поднимается стек на `*.localhost` с HTTPS.
- **P-2:** фичи изолированы друг от друга и от main — контейнеры, тома, порты, данные, код.

В MVP переносятся выводы, а не код. Код агента пишется заново (Docker Engine API вместо CLI, xDS вместо перезапуска Envoy).

## Что реализовано

| Часть | Как в прототипе | Как будет в агенте |
|---|---|---|
| Конфиг | Подмножество `workspace.yaml` v1: модули — папки одного репозитория (`path`), `image`/`build`, `routes`, `uses`, `env`, `hooks.migrate`; сервисы с `port`, `volume`, `expose` | Полный формат, JSON Schema, модули из разных репозиториев |
| Состояние | JSON-файл в `DEVCORB_HOME` (по умолчанию `~/.devcorb-proto`) | DesiredState от сервера / локальный кэш |
| Docker | Сгенерированный compose-файл на окружение + `docker` CLI | Docker Engine API, compose-go |
| Изоляция | Compose project `shop-env-<id>`, свои сеть и тома, метки `com.devcorb.*`, модули не публикуют порты | То же |
| Сети | Сеть на окружение из пула `10.213.N.0/24`, у Envoy в каждой сети адрес `.254` | Решить в ADR-0006 (см. выводы) |
| Simple Isolation | Фича запускает форки и всех, кто от них транзитивно зависит (`uses`). Общие модули и сервисы — сетевые алиасы Envoy в сети фичи, Envoy проксирует их в main (HTTP по имени хоста, TCP по порту) | То же; позже — Contextual Isolation |
| Данные | `database: clone` — у фичи свой экземпляр сервиса БД. Сейчас он пустой: только миграции, без копирования данных main | Логическая БД из золотой копии (P-3) |
| Прокси | Один контейнер Envoy, статический конфиг, перезапуск при каждом изменении | xDS/SDS без перезапуска |
| HTTPS | Свой CA с Name Constraints на `localhost`, сертификат с SAN на каждый хост | То же + установка в хранилища доверия |
| Порты | 80/443, если свободны; иначе запасные 18080/18443, владелец порта называется по имени | + режим сосуществования, privileged helper |
| Git | `git worktree` на фичу, ветка `feature/<slug>`; удаление отказывает при незакоммиченных или незапушенных изменениях | То же |

## Запуск

```bash
cd prototypes/p1-p2
go build -o devcorb .

# пример — отдельный git-репозиторий
cp -R example/shop /tmp/shop && cd /tmp/shop
git init -q -b main && git add -A && git commit -qm init

devcorb doctor
devcorb up
devcorb feature create PAY-123 --modules payments
devcorb list
devcorb routes
curl --cacert ~/.devcorb-proto/ca/ca.pem 'https://pay-123.shop.localhost:18443/api/checkout?amount=7'
devcorb feature rm PAY-123 --force
devcorb down --purge
```

Порт 18443 — запасной режим: на этой машине 80/443 занимает nginx.

## Тесты

```bash
go test ./...                                                    # юнит: план фичи, валидация, слаги, маршруты Envoy
go test -tags integration -run TestIsolation -v -timeout 15m     # нужен Docker
```

Интеграционный тест поднимает main и три фичи на примере `shop` (frontend, backend, payments + Postgres + Mailpit) и проверяет:

1. Фича получает свои копии форкнутых модулей; остальное берётся из main.
2. Backend фичи по логическому имени `http://payments` попадает в платёжку своей фичи.
3. Платёж, созданный в PAY-123, не виден в PAY-124 и в main.
4. Правка файла в worktree UI-7 видна только в UI-7.
5. Общий Mailpit доступен из фичи по имени `mail` через Envoy (TCP).
6. Имена контейнеров содержат ID окружения, ни один модуль не публикует порты на хост, у каждого Postgres свой том.
7. Заголовок `baggage` от клиента отбрасывается на входе и не меняет маршрут.
8. Удаление фичи с незакоммиченными изменениями отклоняется; удаление других фич не трогает данные PAY-123.

После теста в Docker ничего не остаётся: ни контейнеров, ни томов, ни сетей.

## Выводы

1. **Изоляция Docker (P-2) работает** на одной машине без доработок Docker: ID окружения во всех именах, сеть на окружение, порты публикует только Envoy. Гипотеза подтверждена для Docker Desktop. OrbStack, Colima и Podman ещё не проверены.
2. **Simple Isolation реализуема через алиасы Envoy.** Логическое имя общего модуля в сети фичи — алиас Envoy с отдельным IP-адресом. Envoy слушает на этом адресе и отправляет запрос в main. Общий модуль при этом не подключается к сети фичи, поэтому его собственные вызовы не утекают в форки. Это закрывает вопрос «как фича видит main без двусмысленного DNS».
3. **Сеть на окружение расходует пул.** `/16`, нарезанный на `/24`, даёт 255 окружений на машину — для одной машины достаточно. Для ADR-0006 рекомендация меняется на вариант A (сеть на окружение): он проще, а пул не узкое место.
4. **Перезапуск Envoy недопустим даже для MVP.** Каждое создание или удаление фичи на 1,3 с обрывает запросы ко всем окружениям, включая main и чужие фичи. Тест поймал это как падение соседней фичи. xDS (go-control-plane) обязателен с первого релиза.
5. **Порты.** На этой машине 80/443 занимает nginx (brew). Запасной режим на 18080/18443 отработал без вмешательства в nginx — режим сосуществования стоит сделать в MVP: это частый сценарий.
6. **`*.localhost` на macOS 26** резолвится системным резолвером (`::1`, `127.0.0.1`) без `/etc/resolver`. На старых macOS это нужно перепроверить — вывод не переносится автоматически.
7. **Порядок старта важен.** Envoy не запускается, если адрес внутреннего listener ещё не назначен его контейнеру. Поэтому сначала подключаем сети, потом стартуем Envoy. С xDS это снимается: listener добавляется после подключения сети.
8. **Миграции фич.** Если зависимый модуль фичи работает с общей БД, его `migrate` пропускается с предупреждением, как требует `data.md`. В примере такого случая нет, но правило заложено.

## Что не проверено (уходит в другие прототипы)

- Клон данных main в фичу и время на 1 ГБ — **P-3**.
- Contextual Isolation по baggage — **P-5**.
- `*.localhost` и CA внутри контейнеров (CoreDNS) — **P-6**.
- Усыпление, пробуждение, детектор активности — **P-7**.
- Импорт `docker-compose.yml` — **P-8**.
- Envoy на `[::1]`: Docker Desktop публикует порты только на IPv4.

## Проверка на Colima и OrbStack (14.10.2026)

| Runtime | Интеграционный тест | Фича (1 форк + зависимый + Postgres) | Простой всех окружений при перезапуске Envoy |
|---|---|---|---|
| Docker Desktop 29.8 | ✅ | 3,2 с | 1,34 с |
| Colima 0.x (vz, virtiofs) | ✅ | 2,9 с | 1,35 с |
| OrbStack | ✅ 3 из 3 после исправления | 3,1 с | 1,39 с |

**Находка на OrbStack.** Сначала тест падал примерно в половине прогонов: после удаления одной фичи запросы к другой висели до таймаута. Причина — прототип при каждом изменении отключал Envoy от **всех** сетей окружений и подключал заново с тем же IP. При этом Envoy получает новый MAC-адрес, а контейнеры на OrbStack продолжают слать ответы на старый, пока не истечёт ARP-кэш. Исправление: переподключать Envoy только к новым сетям и к тем, где изменились алиасы. После этого — 3 из 3 на OrbStack, без регрессий на Docker Desktop и Colima.

**Вывод для агента:** не трогать сетевые подключения Envoy к неизменившимся окружениям. С xDS это получается само: меняется конфиг, а не сеть.

Colima по умолчанию монтирует в VM только домашнюю папку, поэтому временные каталоги теста пришлось перенести туда. Агенту нужно хранить worktree и данные в `$HOME` или настраивать mounts Colima.
