# Спецификация: `workspace.yaml` v1

**Статус:** черновик · **Версия формата:** 1

> **С 16.10.2026 `workspace.yaml` — не источник правды** ([ADR-0013](../adr/0013-config-on-workspace-server.md)). Конфигурация проектов и сервисов живёт на сервере воркспейса и меняется через `devopus`. Этот формат остаётся:
> - форматом **локального движка** v0.1.0 — до этапа 3, когда режим без воркспейса уйдёт;
> - источником **демо-воркспейса** из [examples/demo](../examples/demo);
> - основой YAML, в котором `devopus project config show` показывает настройки, и личного файла переопределений `devopus.yaml` (спецификация — этап 3).
>
> Импорт для пользователей — только из `docker-compose.yml` (`devopus project create --from-compose`).
>
> Слова этого документа — модели этапа 1: «проект» — тот же проект, «модуль» — приложение, воркспейса в формате нет ([переходный словарь](../docs/product/glossary.md#переход-от-модели-этапа-1)).

Весь стек описывается одним файлом `workspace.yaml`. Формат валидируется JSON Schema — IDE подсказывает поля.

**Обязательные функции v1:** импорт существующего `docker-compose.yml` и экспорт обратно в него.

## Пример

```yaml
version: 1
project: shop
domain: shop.localhost

services:
  mysql:
    image: mysql:8.4
    port: 3306
    data:
      seed: snapshot://shop-anonymized/latest   # обезличенный снапшот
  redis:
    image: redis:7
    port: 6379
  mail:
    image: axllent/mailpit:v1.21
    port: 1025                                  # SMTP для модулей
    ui_port: 8025                               # веб-интерфейс
    expose: mail                                # mail.shop.localhost
  s3:
    image: minio/minio:RELEASE.2025-04-22T22-12-26Z
    port: 9000

modules:
  backend:
    repo: git@github.com:acme/shop-api.git
    runtime: php:8.3
    routes: ["/api"]
    uses: [mysql, redis, mail, s3, payments]
    env:
      CACHE_DRIVER: redis
      QUEUE_CONNECTION: redis
      MAIL_HOST: mail
      PAYMENTS_URL: http://payments            # имя не меняется в фичах
      STRIPE_KEY: ${{ secrets.STRIPE_TEST_KEY }}
    hooks:
      install: composer install
      migrate: php artisan migrate --force
    cron:
      - schedule: "* * * * *"
        command: php artisan schedule:run
    workers:
      - command: php artisan queue:work

  frontend:
    repo: git@github.com:acme/shop-web.git
    runtime: node:22
    routes: ["/"]
    hooks:
      install: npm ci
    command: npm run dev

  payments:
    repo: git@github.com:acme/shop-payments.git
    runtime: python:3.12
    routes: ["/payments"]
    uses: [mysql]
    hooks:
      install: pip install -r requirements.txt
    command: uvicorn app:main --host 0.0.0.0

features:
  database: clone          # clone | shared
  sleep_after: 2h
  cleanup: on_merge
  isolation: simple        # simple | contextual (contextual — этап 3)

overrides:
  allowed: [xdebug, ports]
```

## Корневые поля

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `version` | int | да | Версия формата. Сейчас `1` |
| `project` | string `^[a-z][a-z0-9-]{1,30}$` | да | Имя проекта; используется в именах Docker-ресурсов |
| `domain` | hostname | да | Домен базового окружения. Должен оканчиваться на `.localhost` (или домен платформы) |
| `services` | map<name, Service> | нет | Инфраструктурные зависимости без кода |
| `modules` | map<name, Module> | да (≥1) | Модули проекта |
| `features` | FeaturePolicy | нет | Политика фич |
| `overrides` | OverridePolicy | нет | Что разработчик может менять лично |
| `data` | DataPolicy | нет | *Предложение:* правила маскирования для снапшотов (см. ниже) |

Имена в `services` и `modules` образуют одно пространство имён и являются **логическими DNS-именами** внутри окружения (`http://payments`, `mysql:3306`). Должны быть уникальны и соответствовать `^[a-z][a-z0-9-]{0,62}$` — ограничению DNS-метки. Изначальный лимит в 31 символ оказался надуманным: у Sentry имена до 37 символов ([P-8](../prototypes/p8-compose-import/README.md)).

## Service

| Поле | Тип | Описание |
|---|---|---|
| `image` | string | **Обязателен.** OCI-образ с версией: тег вида версии (`postgres:17.2`) или digest. `latest` и плавающие теги (`redis:alpine`) валидатор не пропускает; импорт закрепляет их по текущему digest (P-8) |
| `port` | int | TCP-порт, к которому подключаются модули; значение `${{ <service>.port }}` |
| `expose` | string | Публикует веб-интерфейс сервиса как `<expose>.<domain>` (и `<expose>.<slug>.<domain>` в фичах) |
| `ui_port` | int | Порт веб-интерфейса для `expose`, если он не совпадает с `port` (Mailpit: SMTP 1025, UI 8025). Без `ui_port` и `port` `expose` — ошибка |
| `data.seed` | URI | Источник данных: `snapshot://<name>/<tag>`, `file://<path>`, `hook://<module>.<hook>` |
| `env` | map | Переменные окружения контейнера |
| `volumes` | list | Именованные тома (namespace'ятся по ID окружения) и bind-монтирования файлов репозитория (`./config/clickhouse.xml:/etc/clickhouse-server/config.d/x.xml`) — у Sentry их 30 (P-8). Bind вне репозитория — только с локальным подтверждением |
| `healthcheck` | object | Как в compose |
| `uses` | list<name> | Зависимости сервиса от других сервисов (Kafka → ZooKeeper); порядок старта (P-8) |
| `optional` | bool | Сервис не поднимается по умолчанию, только по требованию или в фиче, которой он нужен. Аналог compose `profiles`: у Sentry и PostHog по 24–25 таких сервисов (P-8) |
| `entrypoint`, `tmpfs`, `ulimits` | как в compose | Встречаются в 3 из 5 реальных продуктов (P-8) |
| `per_feature` | `clone \| shared \| instance` | *Предложение:* переопределяет `features.database` для конкретного сервиса |

## Module

| Поле | Тип | Описание |
|---|---|---|
| `repo` | git URL | Репозиторий модуля. Взаимоисключимо с `path` |
| `path` | string | Папка внутри основного репозитория (монорепо) |
| `branch` | string | Базовая ветка, по умолчанию `main` |
| `runtime` | `<lang>:<version>` | Рантайм: `php`, `node`, `python`, … Платформа предоставляет образы рантаймов (с `ext-opentelemetry` для PHP). До своих образов — официальный образ языка: `php:8.3` → `php:8.3`, `go:1.25` → `golang:1.25`, `java` → `eclipse-temurin` |
| `image` / `build` | string / object | Альтернатива `runtime`: свой образ или сборка. `build` — объект `{context, dockerfile, target, args}`: строки «папка с Dockerfile» не хватило ни одному из 5 реальных продуктов (P-8) |
| `mount` | path | Куда монтируется код модуля в контейнере. У `runtime` по умолчанию `/app` (он же рабочий каталог); у `image`/`build` по умолчанию никуда — образ несёт код сам. Импорт берёт его из bind-монтирования контекста сборки (`./api:/var/www` → `mount: /var/www`) |
| `routes` | list<path-prefix> | Пути, которые Envoy направляет в модуль на хосте окружения. `/api` берёт `/api` и `/api/…`, но не `/apix`; путь передаётся модулю как есть, без отрезания префикса. Пересечения префиксов между модулями — ошибка валидации (кроме вложенных, где побеждает самый длинный) |
| `port` | int | Порт внутри контейнера, по умолчанию автоопределение / 8080 |
| `uses` | list<name> | Зависимости (сервисы и модули). Граф без циклов для `hooks`; используется для подсказок при форке и порядка старта |
| `env` | map<string, string> | Переменные. Поддерживают выражения `${{ … }}` |
| `command` | string | Команда запуска основного процесса |
| `entrypoint` | string | Как в compose |
| `healthcheck` | object | Как в compose; агент использует его, чтобы понять, что модуль готов |
| `tmpfs`, `ulimits` | как в compose | |
| `optional` | bool | Как у сервиса |
| `hooks.install` | string | Установка зависимостей; запускается при создании worktree и при изменении lock-файлов. Пишет в папку кода или в том модуля (`volumes`): хук работает в отдельном контейнере, всё вне них пропадает |
| `hooks.migrate` | string | Миграции; в фиче — только на собственном клоне БД. Запускается после всех `install`, в порядке `uses`, при новом коммите кода |
| `hooks.seed` | string | *Предложение:* сид-скрипт |
| `hooks.build` | string | *Предложение:* сборка (`npm run build`) |
| `cron` | list<{schedule, command}> | Только у базового окружения и форкнутых модулей |
| `workers` | list<{command, replicas?}> | Фоновые процессы; в фиче читают очереди с префиксом фичи |
| `volumes` | list | Тяжёлые папки (`node_modules`, `vendor`) в именованных томах для скорости на macOS/Windows. Только `имя:/путь`: код даёт worktree |
| `ports` | — | Не поддерживается: наружу доступен только прокси. Валидатор предупреждает и игнорирует |

## Как агент запускает окружение

Реализовано в M4 (`internal/agent/stack` описывает контейнеры, `internal/agent/reconcile` их создаёт). Шаги окружения: `network → certificate → proxy → dns → source → images → services → install → migrate → modules → routes → ready`.

- **Что запускается.** Все модули и сервисы без `optional`, плюс `optional`, которые кто-то из запущенных использует через `uses`.
- **Код.** Модуль с `path` — папка репозитория; с `repo` — клон ветки `branch` в `~/.devopus/src/<проект>/<окружение>/<модуль>`, один раз (агент не делает `pull`). Код монтируется в `mount`.
- **Образы.** `runtime` и `image` скачиваются, если их нет. `build` собирается `docker build` (BuildKit, `.dockerignore`) в `devopus/<проект>-<модуль>:<хеш>`; хеш зависит от Dockerfile и параметров сборки, не от кода. Старые сборки и сборки удалённых проектов агент удаляет.
- **Контейнеры.** Имя `<проект>-env-<окружение>-<имя>`, в сети окружения с алиасом-логическим именем (`db`, `api`), DNS — CoreDNS окружения. Сервисы и модули получают закреплённый адрес в верхней половине `/24` (`.128–.252`, по хешу имени); воркеры — `<модуль>-worker-N` без адреса. У модулей `init: true`. Строка `command`/`entrypoint` разбивается на слова, как в compose; со синтаксисом оболочки (`&&`, `|`, `$VAR`) — `sh -c`.
- **Доверие к CA в модулях.** В контейнер модуля копируются `/devopus/ca.pem` и `/devopus/bundle.pem` (корни Mozilla + локальный CA), заданы `SSL_CERT_FILE`, `CURL_CA_BUNDLE`, `REQUESTS_CA_BUNDLE` (бандл) и `NODE_EXTRA_CA_CERTS` (CA). Сервисам — нет: это чужие образы.
- **Порядок.** Тома → сервисы по `uses` (с `healthcheck` — ждать `healthy`) → `install` всех модулей → `migrate` по `uses` → модули и воркеры → маршруты → готовность: каждый модуль с `routes` ответил через прокси (любым статусом, но ответом модуля, а не Envoy). Модуль, который ещё запускается, оставляет окружение в `creating`, агент проверяет снова; модуль, который упал, — ошибка с его последним выводом.
- **Хуки** запускаются в одноразовом контейнере с образом, кодом, томами, сетью и переменными модуля. Агент помнит, с чем хук прошёл (`~/.devopus/envs/<окружение>/hooks.json`): `install` повторяется при изменении lock-файлов и манифестов (`package-lock.json`, `composer.lock`, `requirements.txt`, `go.sum`, …), `migrate` — при новом коммите; оба — при смене образа, команды или переменных. После хука модуль перезапускается. Вывод — в `~/.devopus/envs/<окружение>/logs/`.
- **Изменения.** Любое изменение того, из чего сделан контейнер (образ, переменные, значения выражений), пересоздаёт его; остальные не трогаются.
- **Остановка и удаление.** `down` останавливает контейнеры (данные в томах остаются, сайт отвечает 503). `down --volumes` удаляет контейнеры, тома, сеть, сертификат, файлы окружения и клоны репозиториев; клон с незакоммиченной или незапушенной работой остаётся на месте (предупреждение в логе агента).
- **Секреты** — из `.env.secrets` рядом с `workspace.yaml` (формат dotenv). Нет значения для `${{ secrets.X }}` — ошибка шага `source`.

## Как агент запускает фичу

Реализовано в M5 (Simple Isolation, [ADR-0005](../adr/0005-isolation-modes.md); план фичи — `internal/agent/stack/feature.go`, запуск — `internal/agent/reconcile/feature.go`). Шаги фичи: `network → certificate → proxy → isolation → dns → source → images → data → services → …` — дальше как у базового окружения; у базового окружения после `migrate` — шаг `golden`.

- **Что фича запускает сама.** Форкнутые модули; модули базового окружения, которые используют их через `uses` (иначе логическое имя форка из них не достать); `optional`-модули, которые им нужны и которых нет в базе. Модули не форкнутые, но запущенные в фиче, работают на коде базовой ветки.
- **Сервисы.** `features.database: clone` — у фичи свои экземпляры всех сервисов, которыми пользуются её модули (и сервисов, от которых зависят они), миграции идут на них. Базы данных (ниже) начинают с копии данных main, остальные сервисы — пустыми. `shared` — фича ходит в сервисы базового окружения; `migrate` модулей, которые пишут в общий сервис, пропускается с заметкой в статусе.
- **Базы данных** (M6, [ADR-0007](../adr/0007-db-cloning.md)). Сервис — база, если его образ — Postgres (`postgres`, `postgis`, `pgvector`, `timescaledb`) или MySQL (`mysql`, `percona-server`), а каталог данных лежит в именованном томе (`pgdata:/var/lib/postgresql/data`; для Postgres 18 — `/var/lib/postgresql`; `PGDATA` учитывается). У базы main есть золотой том, смонтированный в `/devopus/golden`: агент снимает туда копию с работающей базы (`pg_basebackup` от `POSTGRES_USER`, `CLONE LOCAL` от root с `MYSQL_ROOT_PASSWORD`) — когда фиче впервые нужна копия, после изменения миграций main и по `devopus db golden refresh`. Фича (шаг `data`) получает свой том с копией золотого каталога (`cp --reflink=auto`, с проверкой места) и свой контейнер базы с теми же именем БД, пользователем и паролем; её `migrate` идёт по копии. MySQL фичи запускается с бережливыми настройками (`performance_schema=OFF`, buffer pool 32 МБ), если у сервиса нет своей `command`. База без тома и MariaDB копий не получают: фича стартует с пустой (заметка в статусе).
- **Код.** У каждого модуля фичи свой worktree: форки — на ветке фичи, остальные — в detached HEAD на базовой ветке. Модули с `path` — один worktree репозитория проекта на фичу (`~/.devopus/src/<проект>/<фича>/_repo`; если `workspace.yaml` лежит в подпапке репозитория, worktree — всего репозитория). Модули с `repo` — worktree клона базового окружения (`~/.devopus/src/<проект>/<фича>/<модуль>`). Секреты (`.env.secrets`) и файлы, которые монтируют сервисы, берутся из папки проекта, а не из worktree.
- **Как фича видит общее.** Имена модулей и сервисов, которые фича берёт у базового окружения, CoreDNS фичи отдаёт адресом прокси в её сети; прокси различает фичу по адресу назначения и пересылает: модули — по HTTP с выбором по `Host` (несколько модулей на одном порту — можно), сервисы — по TCP. Контейнеры базового окружения в сеть фичи не подключаются, их собственные вызовы остаются в базе (P-2). URL и порты не меняются: `${{ api.url }}` — тот же `http://api:<порт>`.
- **Ограничения общих портов.** Общий модуль не может слушать 443 (и публичный HTTPS-порт), общий сервис — 80/443 и публичные порты прокси; два общих сервиса на одном порту и модуль с сервисом на одном порту — ошибка шага `isolation` с подсказкой форкнуть.
- **Маршруты.** `https://<slug>.<domain>` отдаёт пути модулей фичи из её контейнеров, остальные пути и `expose` — из базового окружения.
- **Слаг** — из имени фичи (`PAY-123` → `pay-123`, `a_b` → `a-b`), уникален в проекте и не совпадает с именами `expose`; при коллизии — суффикс `-2`. В именах ресурсов — только ID.
- **Удаление.** `feature rm` удаляет контейнеры, тома, сеть, сертификат и worktree (ветка остаётся). Сборщик мусора не удаляет worktree, в котором есть незакоммиченные изменения или коммиты вне веток (кроме `feature rm --force`), и не удаляет клон базового окружения, пока на нём держатся worktree фич.
- `down` останавливает и фичи, `up` запускает их снова; `down --volumes` удаляет проект вместе с фичами.

## Жизненный цикл фичи

Реализовано в M7 (`internal/agent/lifecycle`, [P-7](../prototypes/p7-sleep-wake/README.md)).

- **Активность** — запросы через прокси на хосты фичи (Envoy присылает агенту счётчики запросов по кластерам раз в 5 с по тому же mTLS-каналу, что и xDS) и изменения файлов в папках её модулей (обход раз в `sleep_after/4`, не чаще 30 с; без `.git`, `node_modules`, `vendor`, `.venv`, `dist`, `build` и т. п.). Запросы фичи к общим модулям main активностью не считаются.
- **Усыпление** после `features.sleep_after` без активности (по умолчанию `2h`) или `devopus feature sleep`: маршруты фичи переключаются на будильник агента, через секунду контейнеры останавливаются (модули, потом сервисы). Данные в томах остаются. Базовое окружение не засыпает никогда.
- **Пробуждение** — первым запросом или `devopus feature wake`: один запуск на все параллельные запросы, сервисы со своим `healthcheck` — до `healthy`, затем агент ждёт, пока модули с `routes` ответят, и переключает маршруты обратно. Удержанные запросы (с телом) будильник повторяет прямо в модуль. Браузер (`GET` с `Accept: text/html`), если пробуждение дольше 300 мс, получает страницу «Starting …» с автообновлением.
- **Бюджет** — `features.max_running`: если бодрствующих фич проекта больше, засыпают давнее всех использованные (не та, что только проснулась).
- **`cleanup: on_merge`** (по умолчанию): ветка фичи, у которой есть свои коммиты и все они в базовой ветке (`origin/<base>` после периодического `fetch`, иначе локальной), помечается слитой; `feature list` предлагает `feature rm`. Сама фича не удаляется. Squash-merge не распознаётся. `after:<duration>` пока не выполняется.
- Спящая фича сохраняет сеть, worktree, маршруты и сертификат; `down` останавливает её как обычно, `up` после `down` запускает бодрствующей.

## Выражения `${{ … }}`

| Выражение | Значение |
|---|---|
| `${{ secrets.NAME }}` | Секрет воркспейса или проекта; расшифровывается локально агентом |
| `${{ <module>.url }}` | Внутренний URL модуля в текущем окружении (Simple Isolation): в фиче указывает на форк, если он есть, иначе на базу |
| `${{ <module>.host }}`, `${{ <module>.port }}` | Хост/порт модуля в текущем окружении |
| `${{ <service>.host }}`, `${{ <service>.port }}` | Хост/порт сервиса в текущем окружении |
| `${{ env.url }}` | Публичный URL окружения (`https://pay-123.shop.localhost`) |
| `${{ env.slug }}`, `${{ env.id }}` | Слаг и стабильный ID окружения |
| `${{ <service>.database }}` | Имя логической БД окружения (для `clone`) |

Изменение значения выражения (например, добавили модуль в фичу) → агент перезапускает затронутые контейнеры.

## FeaturePolicy (`features`)

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `database` | `clone \| shared` | `clone` | Клонировать БД форкнутого модуля из золотой копии или использовать общую |
| `sleep_after` | duration | `2h` | Усыплять неактивные фичи |
| `cleanup` | `on_merge \| manual \| after:<duration>` | `on_merge` | Автоочистка |
| `isolation` | `simple \| contextual` | `simple` | Режим маршрутизации между модулями |
| `branch_prefix` | string | `feature/` | Префикс ветки |
| `max_running` | int | — | *Предложение:* дефолт бюджета; переопределяется на устройстве |

## OverridePolicy (`overrides`)

| Поле | Описание |
|---|---|
| `allowed` | Список разрешённых личных переопределений: `xdebug`, `ports`, `env:<NAME>`, `resources` |

Overrides хранятся в панели (`Override` = Member × Project) или в локальном `workspace.override.yaml` (в `.gitignore`); всегда видны в панели.

## Правила валидации

1. `version == 1`.
2. Каждое имя в `uses` существует.
3. Нет циклов в графе `uses` среди модулей для порядка хуков (циклы рантайм-вызовов допустимы, но порядок старта тогда — параллельный).
4. Префиксы `routes` не пересекаются (кроме строгой вложенности).
5. Все образы с версией или digest (не `latest` и не плавающий тег вроде `alpine`).
6. Секреты указываются только через `${{ secrets.* }}`; литералы, похожие на ключи, — предупреждение.
7. `domain` в разрешённой зоне.
8. Детектор антипаттернов (предупреждения): `VITE_API_URL`/`NEXT_PUBLIC_API_URL` с абсолютным URL; `ports:` в модулях.
9. Имена `services` и `modules` не пересекаются; сервис зависит только от сервисов; циклы среди сервисов — ошибка, среди модулей — предупреждение.
10. У модуля ровно один источник кода (`repo` или `path`) и ровно один способ запуска (`runtime`, `image` или `build`); модулю на `runtime` нужна `command`.
11. Выражения `${{ }}` ссылаются на существующие имена и атрибуты; ссылка на модуль или сервис вне `uses` — предупреждение (форк не предложит его вместе).

Реализация: JSON Schema — [`schema/workspace.v1.json`](../schema/workspace.v1.json) (встроена в бинарник, `devopus schema`); правила, которые схема не выражает, — `internal/workspace/validate.go`. Ошибки показываются с номером строки.

## Импорт из `docker-compose.yml`

| compose | workspace.yaml |
|---|---|
| сервис с `build:` | `modules.<name>` с `path`/`build` |
| сервис только с `image:` | `services.<name>` |
| `ports:` | отбрасываются (наружу только Envoy); первый HTTP-порт → `port`; предложить `routes` |
| `depends_on` | `uses` |
| `environment`, `env_file` | `env` (значения, похожие на секреты, → предложение вынести в `secrets`) |
| `volumes` (named) | `volumes` |
| `volumes` (bind на код) | заменяется worktree |
| `command` | `command` |

Импорт производит черновик и отчёт о том, что не удалось перенести. Папка `workspace.yaml` — корень репозитория: пути модулей и bind-монтирований считаются от неё, поэтому `devopus init` запускают из корня (compose-файл может лежать глубже, как `docker/docker-compose.dev.yml` у Immich).

Проверено прототипом [P-8](../prototypes/p8-compose-import/README.md) на 5 реальных продуктах (example-voting-app, Mastodon, Sentry self-hosted, Immich, PostHog) и 15 стеках Docker awesome-compose. Все 5 продуктов импортируются без ручных правок, все 20 проектов экспортируются обратно и проходят `docker compose config`.

Дополнительные правила импорта:

| compose | workspace.yaml |
|---|---|
| `profiles` | Сервисы профиля по умолчанию импортируются как обычные, остальные — с `optional: true` |
| `networks` (свои сети) | Сводятся к одной сети окружения; изоляцию даёт Devopus |
| `secrets`, `configs` (файлы) | Bind-монтирование файла репозитория или `${{ secrets.* }}` — предложение в отчёте |
| `extends`, якоря `x-`, `${…}`, `.env` | Разрешаются при загрузке через `compose-go`; переменные хоста без значения — в отчёт |
| `image` без версии | Закрепляется по текущему digest; при отказе реестра (429) — в отчёт с повтором позже |
| Проект без единого `build` | Не целевой: в нём нечего форкать (WordPress, Nextcloud, ELK) |
| Сервис с `depends_on` на модуль (nginx перед php-fpm) | Связь отбрасывается — HTTP маршрутизирует прокси окружения; в отчёт |
| Сервис без `image` и `build` в неактивном профиле (шаблон для `extends`, Immich) | Пропускается; в отчёт |
| `env_file`, которого нет (в репозитории только `.env.example`) | Импорт продолжается; в отчёт |
| Переменная хоста без значения | Подставляется пустой, как в `docker compose`; имя — в отчёт |
| Значения переменных, похожих на секреты | `${{ secrets.NAME }}`; значения дописываются в `.env.secrets` (существующие ключи не трогаются) |
| Приложение запускается на хосте, compose держит только инфраструктуру (PostHog) | Гибридный режим не поддержан; открытый вопрос для пилотов |


## Экспорт в `docker-compose.yml`

Генерирует compose для базового окружения (без Envoy-маршрутизации фич): сервисы, модули с `build`, `depends_on`, env с подставленными значениями (секреты — плейсхолдеры). Гарантия «выход без lock-in».

Детали:
- Прокси нет, поэтому модули с `routes` и сервисы с `expose` публикуются на `127.0.0.1`, каждый на своём порту начиная с 8080 (первым — модуль с `/`). Порты перечислены в шапке файла.
- `${{ secrets.X }}` → `${X}`: запуск `docker compose --env-file .env.secrets up`. `${{ env.url }}` → `http://localhost:<порт модуля с />`, `${{ <service>.database }}` → `POSTGRES_DB`/`MYSQL_DATABASE` сервиса или имя проекта.
- Модуль на `runtime` → официальный образ языка (`php:8.3`), код монтируется в `/app`. Хуки `install` и `migrate` выполняются перед `command` (`sh -c`).
- `workers` → отдельные сервисы `<модуль>-worker-N`; `cron` и `data.seed` не экспортируются (пометка в шапке).
- Модули из `repo` ожидаются в `./<модуль>` — в шапке подсказка, что клонировать.

Проверено: экспорт всех 16 целевых проектов корпуса P-8 проходит `docker compose config`.
