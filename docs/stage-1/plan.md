# План этапа 1 · MVP

**Начат:** 14.10.2026 · Требования — [PRD MVP](../../specs/mvp-prd.md) · CLI — [specs/cli.md](../../specs/cli.md) · Формат — [workspace-yaml.md](../../specs/workspace-yaml.md)

> Этап 1 начат до выполнения критерия перехода (5 LOI). Решение владельца продукта: разработка идёт параллельно с интервью. Первые вехи не зависят от ответов интервью (ADR-0008, гибридный режим, Windows), их можно менять дёшево.

## Вехи

Каждая веха заканчивается рабочим срезом, который можно показать пилотной команде. Порядок выбран так, чтобы сначала шли части без Docker и системных прав, а самое рискованное в реализации (сеть, прокси) — сразу после каркаса агента.

## Раскладка репозитория

| Путь | Что |
|---|---|
| `cmd/devopus` | Бинарник: CLI и (с M2) агент |
| `internal/workspace` | Модель `workspace.yaml`, загрузка, валидация, выражения |
| `internal/compose` | Импорт из compose и экспорт в compose |
| `internal/cli` | Команды CLI |

| `internal/agent/ui` | Локальная панель на `127.0.0.1`: токен и cookie, проверка `Host`, встроенная сборка `dist` (`go:embed`) |
| `web/` | Исходники панели: React + TypeScript, Vite, Tailwind, shadcn/ui, Connect-ES; `npm run build` → `internal/agent/ui/dist`, `npm run gen` → `web/src/gen` из `proto/` ([README](../../web/README.md)) |
| `examples/demo` | Демо-проект: Node, Python и PHP на одном хосте, Postgres, Mailpit |
| `internal/trust` | Доверие к CA в системе: проверка и установка в связку ключей macOS |
| `proto/` → `gen/` | Контракт локального API (Buf + ConnectRPC); `go tool -modfile=tools/go.mod buf generate` |
| `tools/` | Отдельный Go-модуль с buf и плагинами, чтобы не тянуть их в зависимости агента |
| `schema/` | JSON Schema `workspace.yaml` (встроена в бинарник) |
| `prototypes/` | Одноразовый код этапа 0, не импортируется |

### Открытые вопросы M1

- **URL схемы для редактора.** `devopus init` пишет `# yaml-language-server: $schema=https://raw.githubusercontent.com/devopus/devopus/main/schema/workspace.v1.json`. Заработает, когда репозиторий станет публичным под этим именем; после выбора домена — перенести на него (константа `schema.URL`).
- **Образы рантаймов.** `runtime: php:8.3` пока экспортируется в официальный образ языка; собственные образы рантаймов (с `ext-opentelemetry` для PHP) — в M4.

### Решения M2

- **Клиент Docker — `github.com/moby/moby/client`**: `github.com/docker/docker` после v28 устарел. Endpoint определяется как у `docker` CLI: `DOCKER_HOST` → `DOCKER_CONTEXT` или текущий контекст `~/.docker` → `/var/run/docker.sock`; по нему и по `docker info` — Docker Desktop, OrbStack, Colima, Podman.
- **Локальный API — ConnectRPC поверх HTTP/1.1 на unix-сокете.** Те же сообщения `DesiredState`/`EnvironmentStatus`, что в [протоколе агента](../../specs/agent-protocol.md) (ADR-0001). `Watch` шлёт маркер `synced` после начального снимка: клиент меняет желаемое состояние только после него и не теряет прогресс.
- **Агент как служба** — в M9 (`devopus install`); до этого CLI запускает его в фоне, лог — `~/.devopus/agent.log`.
- `down` останавливает окружения (данные и сеть остаются), `down --volumes` удаляет проект со всеми ресурсами.
- ~~Не проверено на OrbStack и Colima~~ — проверено в M3 вместе с прокси.

### Решения M3

- **xDS по TCP с mTLS, а не unix-сокет.** Docker Desktop не пробрасывает произвольные unix-сокеты в VM. Агент слушает только `127.0.0.1:<порт>`, Envoy подключается через `host.docker.internal` (на всех трёх runtime запрос доходит до loopback хоста — проверено). Порт закреплён в `~/.devopus/proxy/xds-port`: он вшит в bootstrap, новый порт означал бы пересоздание прокси. Без mTLS любой локальный процесс мог бы подключиться к xDS и получить приватные ключи сертификатов; поэтому отдельный control CA, Envoy предъявляет клиентский сертификат.
- **Файлы в контейнеры — через `CopyToContainer`, без bind mount.** Не зависит от того, какие каталоги runtime монтирует в VM (Colima — только `$HOME`).
- **Версия конфигурации Envoy — хеш содержимого.** Перезапуск агента собирает ту же конфигурацию с той же версией, Envoy ничего не меняет и не рвёт соединения.
- **Порты прокси закреплены за контейнером.** Смена 80/443 ↔ 18080/18443 меняет все URL, поэтому происходит только при пересоздании прокси: `devopus proxy restart`, включение/выключение сосуществования, или если за время простоя прокси порт занял кто-то другой.
- **Прокси существует, пока есть хотя бы одно окружение.** `down --volumes` последнего проекта освобождает порты.
- **Colima публикует высокие порты только на `127.0.0.1`** (через ssh), `[::1]` молча игнорирует; привилегированные — `limactl` на `*:порт` (оба семейства и LAN). Чтобы `[::1]:18443` не занял кто-то другой (клиенты идут на `::1` первыми, P-6), агент сам слушает `[::1]:порт` и пересылает на `127.0.0.1` — без root, только для портов ≥ 1024. Docker Desktop и OrbStack публикуют `::1` сами, релей там не включается.
- **Агенты с разными `DEVOPUS_HOME` изолированы меткой `com.devopus.instance`** (хеш каталога): тестовый агент рядом с настоящим не удаляет его сети и прокси. Имя прокси для `~/.devopus` — `devopus-proxy`, для других каталогов — с суффиксом экземпляра.

### Решения M4

- **Хуки — одноразовые контейнеры, а не `docker exec` в модуле.** Хук должен пройти до старта модуля (`migrate` раньше, чем приложение начнёт ходить в БД), а модуль на `runtime` без зависимостей не стартует. Значит, `install` пишет в код или в том модуля — так и делают `npm ci`, `composer install`; для Python — venv в томе ([демо](../../examples/demo/workspace.yaml)).
- **Когда повторять хуки** — по отметкам с хешем входов в `~/.devopus/envs/<env>/hooks.json`: `install` — lock-файлы и манифесты, `migrate` — коммит кода; оба — образ, команда, переменные. Иначе хуки шли бы на каждом проходе раз в 30 с.
- **Сборка — `docker build` CLI, а не Engine API.** BuildKit, `.dockerignore`, `--mount=type=cache` и SSH-форвардинг есть только у CLI. Тег зависит от Dockerfile и параметров сборки: код в dev-окружении приходит через `mount`, пересборка на каждое изменение кода не нужна. Минус — агенту нужен `docker` в `PATH` (он есть у всех трёх runtime).
- **Закреплённые IP модулей и сервисов** — `.128–.252` по FNV-хешу имени с линейным пробированием. Добавление модуля почти никогда не сдвигает остальные (пересоздание контейнера = разрыв). Envoy ходит на эти адреса STATIC-кластерами; это же нужно для усыпления (P-7).
- **Готовность — ответ модуля через прокси.** Агент не видит IP контейнеров с хоста на macOS, поэтому спрашивает модуль через Envoy и отличает ответ модуля от собственного 503 Envoy по `x-envoy-upstream-service-time`. Спрашивает только после старта или перезапуска чего-либо: иначе в логе приложения была бы строка раз в 30 с. Проверка, что сайт отдаётся, идёт на `/.devopus/health`, на который отвечает сам Envoy, — не ждёт модулей.
- **Envoy слушает в сетях окружений 80/443 и публичные порты** (`additional_addresses`, `net.ipv4.ip_unprivileged_port_start=0` в контейнере прокси). Тогда `${{ env.url }}` работает изнутри модуля так же, как в браузере, и в режиме fallback (`:18443`). Имя листенера содержит порт: Envoy не меняет адреса листенера на лету.
- **Прерывание прохода.** Долгий `npm ci` не должен держать `devopus down` или `up` другого проекта: изменение желаемого состояния отменяет текущий проход, шаги идемпотентны, следующий проход продолжает. Повторный `up` без изменений не прерывает (сравнение без ревизии), а получает свой проход следом. Прерванный шаг не помечается ошибкой.
- **Клоны модулей из `repo`** — в `~/.devopus/src/<проект>/<env>/<модуль>`, клон во временную папку и переименование. `down --volumes` удаляет клон, только если в нём нет незакоммиченной или незапушенной работы.
- **Colima видит только `$HOME`.** Монтирование папки вне него даёт понятную ошибку с подсказкой `colima start --mount`; Docker Desktop — подсказку про File sharing.

### Открытые вопросы M4

- **curl и headless Chromium внутри модулей.** Они сами отправляют `*.localhost` на `127.0.0.1` (RFC 6761) и не спрашивают DNS — проверено: `curl https://demo.localhost` из контейнера Node даёт отказ соединения, а `fetch`, Python и PHP `file_get_contents` работают. Нужен relay `127.0.0.1:443` → прокси в сетевом пространстве модуля (P-6, «по требованию»). Затрагивает PHP с Guzzle (libcurl). Решить, включать ли его всем модулям или по полю в `workspace.yaml`.
- **`cron` и `data.seed`** валидируются, но не выполняются: `cron` — вместе с жизненным циклом (M7), сиды — с данными (M6).
- **Обновление базового окружения.** Агент клонирует `repo` один раз и не делает `pull`; модуль с `path` работает на той ветке, что открыта в репозитории. Нужна ли команда обновления main (`devopus pull`?) — по отзывам пилотов.
- **Linux: владельцы файлов.** Хуки и модули на `runtime` работают от root в контейнере; на Linux `node_modules`/`vendor` в папке кода окажутся root-овыми. На macOS (virtiofs) проблемы нет. Решать при проверке на Linux (запуск от uid пользователя).
- **Пересборка по изменению кода.** Для модулей с `build` без `mount` (код запечён в образ) изменения кода не видны до пересборки; нужен `devopus up --build` или наблюдение за контекстом.
- **Браузер.** Сквозная проверка — curl и тесты; в браузере демо не открывалось: в связке ключей сейчас корень от прежнего названия (Docklet), корень `~/.devopus` не добавлен (`devopus doctor --fix`).

### Решения M5

- **Общие модули — через прокси по адресу назначения, а не алиасами контейнера прокси.** В P-2 имена общих модулей были сетевыми алиасами Envoy; их смена требует переподключить Envoy к сети фичи (новый MAC, ARP-кэш OrbStack — P-2). Теперь имена отдаёт CoreDNS фичи (`hosts`), а Envoy слушает `0.0.0.0` и выбирает цепочку по `prefix_ranges` (адрес прокси в сети фичи) и `destination_port`. Добавить или убрать общий модуль = обновить xDS и пересоздать DNS-контейнер фичи; сеть и Envoy не трогаются.
- **У каждого модуля фичи свой код.** Зависимые модули (используют форк) работают в своём detached-worktree, а не в папке main: их `install` иначе переписывал бы `vendor`/`node_modules` под работающим main. Цена — диск и время `install` на фичу.
- **`database: clone` до M6 — свои пустые экземпляры всех сервисов модулей фичи.** Свой экземпляр — для всех модулей фичи, а не только форков: имя сервиса в сети фичи одно, и модуль-зависимый с общей и своей БД одновременно получил бы пустую базу без миграций. M6 заменит пустые экземпляры клонами золотой копии; какие сервисы клонировать, а какие делить (Mailpit, Redis), — решать там же (`per_feature`).
- **Ветка фичи остаётся после `feature rm`.** Удаляется только worktree. Поэтому сборщик мусора считает потерей лишь незакоммиченное и коммиты вне веток; строгая проверка (незапушенное, не слитое в базовую ветку) — в `feature rm` без `--force`.
- **`up` запускает и фичи.** `down` останавливает все окружения проекта; без ручного `sleep`/`wake` (M7) иначе фичи после `down`/`up` не вернуть.

### Открытые вопросы M5

- **Команды из worktree фичи.** В монорепо в worktree лежит своя копия `workspace.yaml`; `devopus up` и `feature create` оттуда получат отказ «проект уже зарегистрирован из другой папки». `logs`/`exec`/`feature path` работают (берут имя проекта). Нужно ли узнавать worktree фичи и работать с её проектом — по опыту пилотов и AI-агентов.
- **Worktree всего репозитория.** Если `workspace.yaml` в подпапке большого монорепо, фича получает worktree всего репозитория. Возможный ответ — sparse checkout по папкам модулей.
- **Зависимые модули не обновляются.** Их код заморожен на коммите базовой ветки в момент создания фичи; обновления main до них не доходят (как и до клонов базы — открытый вопрос M4).
- **gRPC и HTTP/2 к общим модулям.** Прокси ходит к общему модулю по HTTP/1.1; gRPC между модулями фичи и main не пройдёт. Нужен признак протокола модуля (или `http2_protocol_options` по полю в `workspace.yaml`). WebSocket работает.
- **Пустые данные в фиче** до M6: модуль без сида видит пустую БД. Подсказка про `features.database: shared` есть в спецификации, но не в выводе CLI.

### Решения M6

- **Postgres — тоже отдельный инстанс из копии каталога, а не логическая база в общем инстансе** (ADR-0007, дополнение): имя БД в фиче не меняется, работают проекты с литеральным `DATABASE_URL` из compose. Золотая копия — `pg_basebackup` без остановки main вместо `ALLOW_CONNECTIONS false` + `TEMPLATE`.
- **Скрипты копирования выполняются в образе самой базы** (`docker exec` в базу main, одноразовый контейнер для копии фичи): нужные утилиты (`pg_basebackup`, `mysql`, `cp`, `df`) уже там, лишних образов не скачиваем. Busybox `cp` (Alpine) без `--reflink` — запасной `cp -a`.
- **Золотая копия ленивая.** Без фич main не тратит время на копию при каждом `up`; первая фича ждёт её (≈1 с на 1 ГБ).
- **Копии фич не догоняют main сами.** После миграций main копия фичи отстаёт (`db lag`), но не пересоздаётся без `db reset`: в ней работа разработчика.

### Открытые вопросы M6

- **Сиды (`data.seed`, `hooks.seed`)** по-прежнему не выполняются: пустая main — пустые копии. Снапшоты — этап 2.
- **MariaDB, MySQL без clone plugin, MongoDB, Redis** — копий нет, фича получает пустой экземпляр. `mariabackup` для MariaDB, `BGSAVE`-копия для Redis — по запросам пилотов.
- **Золотая копия — весь инстанс.** `pg_basebackup` копирует все базы инстанса и WAL; при нескольких больших базах в одном Postgres это лишнее место. Возможна логическая БД в общем инстансе как оптимизация для проектов с `${{ db.database }}`.
- **Диск без reflink.** Каждая фича — полная копия (10 фич × 5 ГБ = 50 ГБ). Проверка места есть, бюджета диска нет — с жизненным циклом (M7).
- **Пароль root MySQL** нужен в `MYSQL_ROOT_PASSWORD` сервиса; при `MYSQL_RANDOM_ROOT_PASSWORD` копия не снимется (ошибка шага `golden`).

### Решения M7

- **Переключение сна — маршрутом (RDS), а не здоровьем эндпоинта.** Схема P-7 (агрегатный кластер «модуль → будильник» + здоровье от агента через EDS) на xDS давала устаревшее состояние на части рабочих потоков Envoy: Envoy подтверждал «модуль нездоров», а отдельные запросы ещё секунды шли в остановленный контейнер. Таблица маршрутов обновляется на всех потоках сразу; на оставшееся окно — секунда паузы между переключением и `docker stop`, а пришедшее к будильнику, когда фича уже проснулась, он просто повторяет в модуль.
- **Будильник на хосте, а не в контейнере.** Он — часть агента; Envoy ходит к нему, как к xDS, через `host.docker.internal`. Агент не видит IP контейнеров на macOS, поэтому удержанные запросы повторяет через прокси (служебный заголовок → маршрут прямо в модуль). Таймаут подключения к будильнику — 15 с: Colima пробрасывает соединения из VM к хосту по одному, и всплеск запросов подключается не сразу.
- **Активность по запросам — счётчики Envoy через stats sink** (metrics service) по тому же mTLS-соединению, что xDS, с фильтром только на `cluster.*.upstream_rq_total`. Admin-интерфейс Envoy наружу не открываем. Изменения файлов — обход папок модулей, не FSEvents/inotify (как в P-7).
- **MAC контейнера закреплён за IP (`02:42:<ip>`).** После `docker stop/start` Docker выдаёт новый MAC, и соседи по сети, включая прокси, какое-то время шлют пакеты на старый (это же видели в P-2 на OrbStack). Контейнеры с закреплённым IP пересоздаются один раз при обновлении агента.
- **Сон — не желаемое состояние, а дело агента.** Желаемое — «фича нужна»; спит она или нет, решает агент (и `feature sleep/wake`), состояние переживает перезапуск агента.

### Открытые вопросы M7

- **`cleanup: after:<duration>`** валидируется, но не выполняется; автоудаление фич — по запросам пилотов (с той же проверкой несохранённой работы).
- **Squash-merge** не распознаётся как слияние (нет общей истории); нужен API хостинга (GitHub/GitLab) — этап 2.
- **WebSocket и gRPC к спящей фиче**: будильник повторяет только обычные HTTP-запросы; апгрейд соединения разбудит фичу, но первое соединение получит ошибку.
- **Воркеры и очереди спящей фичи** стоят; сообщения в её очередях копятся, `cron` не выполняется (и вообще пока не реализован).
- **Бюджет устройства** (RAM/диск на все проекты) — только `max_running` на проект; панель и бюджет устройства — M8/M9.
- **Активность из файлов** — обход папок; для больших монорепо нужны FSEvents/inotify. Приложение, которое само пишет в папку кода (логи, кеш вне списка исключений), не даст фиче уснуть.

### Решения M8

- **Панель — на `127.0.0.1` агента с токеном, а не за Envoy на `https://devopus.localhost`.** Через прокси панель зависела бы от портов 80/443 (fallback 18443), сертификата и доверия к CA — ровно того, что панель должна помогать чинить. Любая страница в браузере может слать запросы на `127.0.0.1`, поэтому API панели — только с токеном: `devopus ui` открывает `/auth?token=…`, агент ставит cookie `HttpOnly; SameSite=Strict`; запросы с чужим `Host` (DNS rebinding) и чужим `Origin` отклоняются. Токен лежит в `~/.devopus/panel-token` (0600) и не меняется между перезапусками, порт закреплён — открытая вкладка переживает перезапуск агента.
- **Тот же API, что у CLI**, без отдельного REST: ConnectRPC работает из браузера по HTTP/1.1, включая серверные потоки (`Watch`, `Logs`). Типы для TypeScript — `protoc-gen-es` из того же `proto/`.
- **Панель читает `workspace.yaml` с диска.** У браузера нет файла проекта, поэтому `Up`, `CreateFeature`, `AddFeatureModules` и `DescribeProject` принимают имя проекта и берут файл из папки, откуда проект зарегистрирован, — как это сделал бы CLI. Файл с ошибками — ошибка в панели, а не тихо старая копия из `state.json`.
- **Сборка панели закоммичена** (`internal/agent/ui/dist`): `go build` и `go install` работают без Node. Цена — пересобирать `dist` вместе с правками `web/`; проверка в CI — с M9.
- **Без TanStack Router/Query**, в отличие от [tech-stack](../architecture/tech-stack.md) для облачной панели: у локальной один экран, выбранное окружение — в `#хеше` URL, состояние окружений приходит потоком `Watch`, остальное — `Status` раз в 5 с.
- **stderr в логах — отметка на полях, а не красный текст**: многие серверы (Python `http.server`, PHP) пишут в stderr каждый запрос.

### Открытые вопросы M8

- **Playwright-тесты панели** ([tech-stack](../architecture/tech-stack.md)) не написаны: сценарий проверен вручную в Chrome. Автотест «US-4 из панели» — вместе с CI (M9).
- **`exec` в панели** (терминал на xterm.js) не сделан: нужен двунаправленный поток, ConnectRPC из браузера его не даёт — WebSocket к агенту.
- **Состояния модулей после пробуждения** обновляются со следующим проходом reconcile (несколько секунд): фаза уже `running`, а модули ещё `exited`.
- **Бюджет устройства** (RAM и диск на все проекты) в панели не показан: ресурсы — по окружению.
- **Сообщения агента для CLI** («remove the feature with --force») показываются в панели как есть.

### Открытые вопросы M3
