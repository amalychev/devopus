# План этапа 1 · MVP

**Начат:** 14.10.2026 · Требования — [PRD MVP](../../specs/mvp-prd.md) · CLI — [specs/cli.md](../../specs/cli.md) · Формат — [workspace-yaml.md](../../specs/workspace-yaml.md)

> Этап 1 начат до выполнения критерия перехода (5 LOI). Решение владельца продукта: разработка идёт параллельно с интервью. Первые вехи не зависят от ответов интервью (ADR-0008, гибридный режим, Windows), их можно менять дёшево.

## Вехи

Каждая веха заканчивается рабочим срезом, который можно показать пилотной команде. Порядок выбран так, чтобы сначала шли части без Docker и системных прав, а самое рискованное в реализации (сеть, прокси) — сразу после каркаса агента.

### Открытые вопросы M1

- **URL схемы для редактора.** `devcorb init` пишет `# yaml-language-server: $schema=https://raw.githubusercontent.com/devcorb/devcorb/main/schema/workspace.v1.json`. Заработает, когда репозиторий станет публичным под этим именем; после выбора домена — перенести на него (константа `schema.URL`).
- **Образы рантаймов.** `runtime: php:8.3` пока экспортируется в официальный образ языка; собственные образы рантаймов (с `ext-opentelemetry` для PHP) — в M4.

### Решения M2

- **Клиент Docker — `github.com/moby/moby/client`**: `github.com/docker/docker` после v28 устарел. Endpoint определяется как у `docker` CLI: `DOCKER_HOST` → `DOCKER_CONTEXT` или текущий контекст `~/.docker` → `/var/run/docker.sock`; по нему и по `docker info` — Docker Desktop, OrbStack, Colima, Podman.
- **Локальный API — ConnectRPC поверх HTTP/1.1 на unix-сокете.** Те же сообщения `DesiredState`/`EnvironmentStatus`, что в [протоколе агента](../../specs/agent-protocol.md) (ADR-0001). `Watch` шлёт маркер `synced` после начального снимка: клиент меняет желаемое состояние только после него и не теряет прогресс.
- **Агент как служба** — в M9 (`devcorb install`); до этого CLI запускает его в фоне, лог — `~/.devcorb/agent.log`.
- `down` останавливает окружения (данные и сеть остаются), `down --volumes` удаляет проект со всеми ресурсами.
- ~~Не проверено на OrbStack и Colima~~ — проверено в M3 вместе с прокси.

### Решения M3

- **xDS по TCP с mTLS, а не unix-сокет.** Docker Desktop не пробрасывает произвольные unix-сокеты в VM. Агент слушает только `127.0.0.1:<порт>`, Envoy подключается через `host.docker.internal` (на всех трёх runtime запрос доходит до loopback хоста — проверено). Порт закреплён в `~/.devcorb/proxy/xds-port`: он вшит в bootstrap, новый порт означал бы пересоздание прокси. Без mTLS любой локальный процесс мог бы подключиться к xDS и получить приватные ключи сертификатов; поэтому отдельный control CA, Envoy предъявляет клиентский сертификат.
- **Файлы в контейнеры — через `CopyToContainer`, без bind mount.** Не зависит от того, какие каталоги runtime монтирует в VM (Colima — только `$HOME`).
- **Версия конфигурации Envoy — хеш содержимого.** Перезапуск агента собирает ту же конфигурацию с той же версией, Envoy ничего не меняет и не рвёт соединения.
- **Порты прокси закреплены за контейнером.** Смена 80/443 ↔ 18080/18443 меняет все URL, поэтому происходит только при пересоздании прокси: `devcorb proxy restart`, включение/выключение сосуществования, или если за время простоя прокси порт занял кто-то другой.
- **Прокси существует, пока есть хотя бы одно окружение.** `down --volumes` последнего проекта освобождает порты.
- **Colima публикует высокие порты только на `127.0.0.1`** (через ssh), `[::1]` молча игнорирует; привилегированные — `limactl` на `*:порт` (оба семейства и LAN). Чтобы `[::1]:18443` не занял кто-то другой (клиенты идут на `::1` первыми, P-6), агент сам слушает `[::1]:порт` и пересылает на `127.0.0.1` — без root, только для портов ≥ 1024. Docker Desktop и OrbStack публикуют `::1` сами, релей там не включается.
- **Агенты с разными `DEVCORB_HOME` изолированы меткой `com.devcorb.instance`** (хеш каталога): тестовый агент рядом с настоящим не удаляет его сети и прокси. Имя прокси для `~/.devcorb` — `devcorb-proxy`, для других каталогов — с суффиксом экземпляра.

### Решения M4

- **Хуки — одноразовые контейнеры, а не `docker exec` в модуле.** Хук должен пройти до старта модуля (`migrate` раньше, чем приложение начнёт ходить в БД), а модуль на `runtime` без зависимостей не стартует. Значит, `install` пишет в код или в том модуля — так и делают `npm ci`, `composer install`; для Python — venv в томе ([демо](../../examples/demo/workspace.yaml)).
- **Когда повторять хуки** — по отметкам с хешем входов в `~/.devcorb/envs/<env>/hooks.json`: `install` — lock-файлы и манифесты, `migrate` — коммит кода; оба — образ, команда, переменные. Иначе хуки шли бы на каждом проходе раз в 30 с.
- **Сборка — `docker build` CLI, а не Engine API.** BuildKit, `.dockerignore`, `--mount=type=cache` и SSH-форвардинг есть только у CLI. Тег зависит от Dockerfile и параметров сборки: код в dev-окружении приходит через `mount`, пересборка на каждое изменение кода не нужна. Минус — агенту нужен `docker` в `PATH` (он есть у всех трёх runtime).
- **Закреплённые IP модулей и сервисов** — `.128–.252` по FNV-хешу имени с линейным пробированием. Добавление модуля почти никогда не сдвигает остальные (пересоздание контейнера = разрыв). Envoy ходит на эти адреса STATIC-кластерами; это же нужно для усыпления (P-7).
- **Готовность — ответ модуля через прокси.** Агент не видит IP контейнеров с хоста на macOS, поэтому спрашивает модуль через Envoy и отличает ответ модуля от собственного 503 Envoy по `x-envoy-upstream-service-time`. Спрашивает только после старта или перезапуска чего-либо: иначе в логе приложения была бы строка раз в 30 с. Проверка, что сайт отдаётся, идёт на `/.devcorb/health`, на который отвечает сам Envoy, — не ждёт модулей.
- **Envoy слушает в сетях окружений 80/443 и публичные порты** (`additional_addresses`, `net.ipv4.ip_unprivileged_port_start=0` в контейнере прокси). Тогда `${{ env.url }}` работает изнутри модуля так же, как в браузере, и в режиме fallback (`:18443`). Имя листенера содержит порт: Envoy не меняет адреса листенера на лету.
- **Прерывание прохода.** Долгий `npm ci` не должен держать `devcorb down` или `up` другого проекта: изменение желаемого состояния отменяет текущий проход, шаги идемпотентны, следующий проход продолжает. Повторный `up` без изменений не прерывает (сравнение без ревизии), а получает свой проход следом. Прерванный шаг не помечается ошибкой.
- **Клоны модулей из `repo`** — в `~/.devcorb/src/<проект>/<env>/<модуль>`, клон во временную папку и переименование. `down --volumes` удаляет клон, только если в нём нет незакоммиченной или незапушенной работы.
- **Colima видит только `$HOME`.** Монтирование папки вне него даёт понятную ошибку с подсказкой `colima start --mount`; Docker Desktop — подсказку про File sharing.

### Открытые вопросы M4

- **curl и headless Chromium внутри модулей.** Они сами отправляют `*.localhost` на `127.0.0.1` (RFC 6761) и не спрашивают DNS — проверено: `curl https://demo.localhost` из контейнера Node даёт отказ соединения, а `fetch`, Python и PHP `file_get_contents` работают. Нужен relay `127.0.0.1:443` → прокси в сетевом пространстве модуля (P-6, «по требованию»). Затрагивает PHP с Guzzle (libcurl). Решить, включать ли его всем модулям или по полю в `workspace.yaml`.
- **`cron` и `data.seed`** валидируются, но не выполняются: `cron` — вместе с жизненным циклом (M7), сиды — с данными (M6).
- **Обновление базового окружения.** Агент клонирует `repo` один раз и не делает `pull`; модуль с `path` работает на той ветке, что открыта в репозитории. Нужна ли команда обновления main (`devcorb pull`?) — по отзывам пилотов.
- **Linux: владельцы файлов.** Хуки и модули на `runtime` работают от root в контейнере; на Linux `node_modules`/`vendor` в папке кода окажутся root-овыми. На macOS (virtiofs) проблемы нет. Решать при проверке на Linux (запуск от uid пользователя).
- **Пересборка по изменению кода.** Для модулей с `build` без `mount` (код запечён в образ) изменения кода не видны до пересборки; нужен `devcorb up --build` или наблюдение за контекстом.
- **Браузер.** Сквозная проверка — curl и тесты; в браузере демо не открывалось: в связке ключей сейчас корень от прежнего названия (Docklet), корень `~/.devcorb` не добавлен (`devcorb doctor --fix`).

### Открытые вопросы M3

- **Браузеры по отдельности.** Страница открылась без предупреждения в браузере владельца; Chrome, Safari и Firefox поодиночке не сверены (Firefox берёт CA из связки ключей при `security.enterprise_roots.enabled`).
- ~~**Не модуль, а страница прокси.**~~ Модули за прокси — M4.
- ~~**CA в контейнерах** и **relay `127.0.0.1:443` для curl/headless Chromium** — M4.~~ CA в контейнерах модулей и DNS — сделаны в M4; relay — открытый вопрос M4.
- **Linux-хост не проверен** (нет машины): `host.docker.internal:host-gateway` задан, но агент слушает xDS на `127.0.0.1` хоста, а с Linux-моста это не loopback. Вероятное решение — слушать на адресе моста `docker0` или запускать Envoy с `network_mode: host`; решить при проверке на Linux.
