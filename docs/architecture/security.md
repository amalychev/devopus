# Безопасность, приватность, compliance

Сайт, который удалённо управляет Docker на машине разработчика, по сути даёт удалённое выполнение кода. Защита строится слоями.

## Модель угроз

| # | Угроза | Последствие | Контрмеры |
|---|---|---|---|
| T1 | Взлом платформы (Core / Agent gateway) | Доступ к машинам всех клиентов — **критично** | Агент исполняет только типизированные действия из белого списка; DesiredState и конфиги подписаны; опасные действия требуют локального подтверждения; внешний пентест |
| T2 | Злонамеренный участник воркспейса меняет `workspace.yaml` | Произвольный образ/mount на машинах коллег | Политики образов (allowlist реестров); новый образ и mount вне проекта — локальное подтверждение; аудит-лог |
| T3 | Украденный токен устройства | Получение секретов команды | Device flow, отзыв в один клик, привязка к ключу устройства, ротация ключа команды при отзыве |
| T4 | Утечка ПДн из снапшотов БД | Регуляторные риски | Обезличивание в CI клиента; шифрование ключом команды; хранение в S3 клиента |
| T5 | Кража ключа локального CA | Подделка любых сайтов | Name Constraints на `.localhost` и домены платформы; двухуровневый CA — корень подписывает ограниченный промежуточный, ключ корня уничтожается: Java не проверяет ограничения корня (P-6); права только для агента |
| T6 | Доступ к окружениям из локальной сети | Утечка данных | Слушать только `127.0.0.1`/`::1`, никогда `0.0.0.0` |
| T7 | Подмена `baggage: feature=…` | Доступ к чужой фиче (превью, Tunnel) | Envoy удаляет входящий ключ на границе и выставляет сам |
| T8 | Подмена релиза агента | RCE на машинах | Подпись релизов Sigstore/cosign, проверка при автообновлении |
| T9 | Вредоносный хук в конфиге (`hooks`, `command`) | Выполнение кода внутри контейнера | Хуки исполняются только внутри контейнеров модуля, не на хосте; изменения хуков видны в diff и аудит-логе |

## Принципы

- **Типизированные действия, не shell.** Агент умеет: создать worktree, поднять сервис из разрешённого образа, показать логи, перезапустить сервис, снять снапшот. Никакого произвольного shell и произвольных mount'ов от сервера.
- **Локальное подтверждение** опасных действий: новый образ, доступ к папке вне проекта, удаление worktree с незапушенными изменениями, остановка чужой службы, изменение системных настроек (DNS, CA, sysctl).
- **Серверы админа** ([ADR-0019](../../adr/0019-admin-servers.md)): входят токеном устройства, полученным за одноразовый код; токен работает только в своём воркспейсе и только для потока настроек, отчёта и ключа устройства; агент сервера применяет только версии, подписанные доверенными людьми, — даже первую и даже обычную правку.
- **Только исходящие соединения.** Агент сам открывает WebSocket; входящих портов на машине нет.
- **Подпись.** Релизы агента и DesiredState подписаны; агент проверяет подпись.
- **Новый код — только с согласия разработчика** ([ADR-0017](../../adr/0017-confirm-new-code.md), риск R21). Версия настроек, после которой машина запустит новое — образ не из каталога, команду, хук, сборку, папку хоста, другой репозиторий, новое приложение, — ждёт `devopus changes accept`; проект тем временем работает на прежней. Повседневные правки тимлида (версии каталожных сервисов, переменные, маршруты) и свои правки автора применяются сразу. Второй слой — подписи ([ADR-0018](../../adr/0018-signed-settings.md)): версию подписывает устройство автора, и только если сервер вернул ровно его правку; агент проверяет подпись по корню доверия (ключ устройства админа), который запомнил при первом знакомстве с воркспейсом, и применяет подписанное подтверждёнными устройствами без вопросов.

## Секреты: E2E-шифрование

**Сделано в R8** — [ADR-0009](../../adr/0009-secrets-key-distribution.md), `internal/secrets`.

- age (X25519), ключ на воркспейс. Сервер хранит шифртексты, но прочитать их не может.
- У каждого устройства своя пара ключей: приватная часть — в Keychain / Secret Service, публичная — на сервере.
- Секрет в конфиге: `${{ secrets.STRIPE_TEST_KEY }}`; агент расшифровывает его локально и подставляет в env контейнера.
- Ключ доставляют агенты админа и тимлидов, которые держат его сами (вариант A); запасной путь — код восстановления (`devopus secrets recover`, вариант C). Ротация — `devopus secrets rotate`.

### Доставка ключа команды на новое устройство

Ключ команды должен быть «обёрнут» публичным ключом нового устройства кем-то, кто им уже владеет. Варианты:

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Любое онлайн-устройство админа автоматически оборачивает ключ после подтверждения инвайта в панели | Быстро, E2E сохраняется | Нужен онлайн-агент админа или общий сервер команды |
| B. Общий сервер команды (Device, привязанный к Workspace) работает как «key custodian» | Не зависит от людей | Ещё одна точка доверия |
| C. Ключ команды восстанавливается из recovery-фразы, которую админ вводит в браузере (WebCrypto) и оборачивает для устройства | Не требует онлайн-агентов | Шаг вручную, задержка |

Рекомендация: A с fallback C; решение — [ADR-0009](../../adr/0009-secrets-key-distribution.md).

**Ротация** ключа команды при отзыве устройства/участника: новый ключ, перешифровка всех секретов на клиенте админа, переобёртка для активных устройств.

## Приватность

Исходный код и данные проектов не покидают машину разработчика — главное отличие от облачных сред.

| Данные | Где хранятся | Кто видит |
|---|---|---|
| Исходный код | Устройство и git-хостинг клиента | Платформа не видит |
| БД окружений | Устройство | Платформа не видит |
| Снапшоты для онбординга | S3 клиента или у нас, зашифрованы ключом команды | Только участники воркспейса |
| Секреты | Сервер, E2E | Только агенты воркспейса |
| `workspace.yaml` | Сервер и git | Участники воркспейса |
| Логи окружений | Сервер, срок хранения настраивается; стриминг отключаемый | Участники воркспейса |
| Телеметрия агента | Сервер, без путей и содержимого, отключаемая | Команда платформы |

## Compliance

- **GDPR.** Персональные данные платформы — только аккаунты участников. DPA для клиентов, выбор региона хранения (ЕС / США), удаление воркспейса по запросу.
- **SOC 2 Type II.** Нужен для продаж средним и крупным компаниям. Контроли (аудит-лог, доступы, бэкапы) закладываются с первой версии, аудит — при первых крупных клиентах (этап 4).
- **Self-hosted** (после облачной версии). «Пульт» воркспейса — настройки и веб-панель — ставится на сервер клиента командой `devopus server install` ([ADR-0016](../../adr/0016-workspace-server.md)); учётные записи — в облачном Auth, Auth внутри инсталляции — Enterprise. Код и данные проектов на сервер воркспейса не попадают и в облачном варианте.

Подробно — [auth.md](auth.md) и [роли](../product/roles.md).

| Что | Как |
|---|---|
| Регистрация и вход | Email + одноразовый код в CLI; браузер с PKCE или device flow (RFC 8628). SSO/SAML — позже, через Auth как брокер |

| Агент на ПК | Работает от имени пользователя, с его правами |
| Агент на сервере админа (staging, production) | Токен устройства, выданный админом |
| Роли | Админ (воркспейс), тимлид и разработчик (проект); права сверх роли выдаются явно |
| Проверка прав | Только на сервере воркспейса, на каждом запросе, одинаково для CLI и веб-интерфейса |
