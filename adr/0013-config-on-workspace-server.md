# ADR-0013: Конфигурация окружения живёт на сервере воркспейса; YAML — просмотр и переопределения

**Статус:** Accepted (16.10.2026). Заменяет [ADR-0008](0008-config-location.md).

## Контекст

На этапе 1 весь стек описывался файлом `workspace.yaml` в git-репозитории: кто правил файл, тот и менял окружение, а каждый разработчик поднимал его сам (`devopus init`, `devopus up`). Владелец продукта сформулировал модель иначе ([vision](../docs/product/vision.md)):

- окружением команды управляют **админ и тимлиды**, у разработчиков оно синхронизируется само;
- **воркспейс → проект → приложения и сервисы:** проект — продукт (Google Drive), приложение — репозиторий (frontend, backend), сервис существует в проекте и подключается к нескольким приложениям; настройки живут на сервере Devopus;
- всё, что делается в CLI, потом будет и в веб-интерфейсе.

Если источник правды — файл в git, у одного человека не может быть права менять окружение команды, а у другого — не может. Права в git — это права на репозиторий, а не на инфраструктуру.

## Решение

1. **Источник правды — сервер воркспейса.** Проекты, сервисы, их версии и настройки хранятся там, версионируются и меняются только через `devopus` (CLI или веб-интерфейс) людьми с нужными правами ([ADR-0015](0015-roles-and-permissions.md)).
2. **Агенты на ПК разработчиков получают конфигурацию с сервера** и приводят Docker к ней ([ADR-0001](0001-desired-state-reconciliation.md)). Изменение тимлида раскатывается всем без действий с их стороны.
3. **YAML нужен для двух вещей:**
   - **просмотр и экспорт:** `devopus project config show` и страница проекта в веб-интерфейсе показывают текущую конфигурацию в YAML;
   - **личные переопределения:** файл `devopus.local.yaml` в папке проекта перекрывает часть настроек (например, версию PHP или Node), если разработчик не согласен с конфигурацией. Файл **только личный**: он в `.gitignore` и действует только на машине этого разработчика. Что можно перекрывать, решают права и политика проекта; переопределения видны в веб-интерфейсе как расхождения.
4. **Режима без воркспейса нет.** Даже один человек работает через свой воркспейс (он же админ); для отладки и разработки Devopus есть демо-воркспейс. `workspace.yaml` этапа 1 перестаёт быть рабочим форматом; из `docker-compose.yml` проект создаётся на сервере одной командой (импорт).

## Последствия

- Онбординг: вход, установка агента, проекты воркспейса поднимаются сами. Ни `init`, ни `.env.secrets` вручную.
- Агенту нужна связь с сервером воркспейса. Без сети он работает с последней полученной конфигурацией.
- Команды этапа 1 `init`, `validate`, `export compose`, `schema` уходят: импорт compose — в `devopus project create --from-compose`.
- Двусторонняя синхронизация конфигурации с git (бывший план этапа 2) больше не нужна.
- Переопределение, которое политика проекта не разрешает, агент не применяет и объясняет почему.
