# ADR-0019: Сервер админа — участник воркспейса особого вида с токеном устройства; он применяет только подписанное

**Статус:** Accepted (17.10.2026). Этап 5 roadmap, шаг R13; публичные адреса и сертификаты — R14.

## Контекст

Админ хочет разворачивать те же проекты на своих серверах — staging, production — теми же настройками, что у разработчиков ([ADR-0016](0016-workspace-server.md), п. 4). На сервере никто не входит в Devopus: нужен способ подключить машину, а не человека. При этом сервер — самое ценное, что есть у команды, и риск R20 требует для него: только pull, подпись изменений ключом админа, никакого удалённого `exec`.

## Решение

1. **Сервер — участник воркспейса особого вида.** Это строка пользователя `srv_…` с ролью `server` в воркспейсе и в тех проектах, которые он запускает. Поэтому устройства, ключи устройств, доставка ключа секретов и отчёты о статусе работают для него так же, как для людей, без отдельного кода. Права роли `server` — только `env.use` и `secrets.read` в своих проектах. В списках участников сервера не видно, у него свой список: `devopus servers list`.
2. **Подключение одноразовым кодом.** `devopus servers add <имя> --project …` (право `servers.manage` во всех его проектах; сервер без проектов — только админ) даёт код на час. На сервере `sudo devopus agent install --server --url … --join <код>` меняет код на **токен устройства** (`dvs_…`; сервер хранит только хеш) и ставит агента системной службой `devopus-agent` (root: Docker и порты 80/443) с данными в `/var/lib/devopus-agent`, токен лежит в `server.json` с правами `0600`.
3. **Токен сервера узкий.** Он работает только в своём воркспейсе и только для трёх методов: поток настроек, отчёт о статусе, регистрация ключа устройства. Прочитать настройки чужих проектов, участников или аудит с ним нельзя. `devopus servers rm` отзывает токен сразу: агент отключается и останавливает проекты.
4. **Только подписанное ([ADR-0018](0018-signed-settings.md)).** Агент сервера работает в строгом режиме: версия без подписи корня или подтверждённого устройства не применяется вообще. Не применяются ни первая версия, ни обычная правка вроде переменной или версии каталожного сервиса. Неподписанная первая версия не берётся совсем — в журнале агента указано почему. Последующие неподписанные ждут, и админ может принять их на самом сервере: `sudo devopus changes accept`. Команды с сервера по-прежнему не выполняются, всё идёт только через настройки (pull).
5. **На сервере никто не входит.** `sudo devopus status` и `sudo devopus changes` работают с агентом сервера без входа: CLI под root находит его папку данных сам.

## Последствия

- Staging разворачивается из тех же настроек, что у разработчиков, а меняется только подписанными правками людей, которым админ доверяет.
- Код приложений сервер клонирует своим доступом к git: админ даёт ему deploy key. Ключи разработчиков на сервер не попадают.
- Секреты доходят до сервера, как до нового разработчика: ключ воркспейса для него оборачивает агент админа или тимлида.
- **Пока не сделано (R14):** публичный адрес проекта на сервере, сертификаты Let's Encrypt, обновление без простоя, откат, отдельное право и подтверждение для production. Сейчас проект на сервере доступен по локальному адресу (`*.localhost`) самого сервера.
